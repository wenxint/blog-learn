## A. 数据库与 SQL（8 题）

**A1. `BIGINT UNSIGNED AUTO_INCREMENT` 和 `INT` 做主键，为什么选前者？**
<details><summary>答案</summary>
`INT` 上限约 21 亿，日志类表几年就可能用完；用完了再改主键类型要锁表。`UNSIGNED` 是为了不要负数（id 不会是 -1）。`BIGINT` 上限 1844 京，够用到人类消失。
</details>

**A2. 为什么 MySQL 里要用 `utf8mb4` 而不是 `utf8`？**
<details><summary>答案</summary>
MySQL 的 `utf8` 是 `utf8mb3` 的别名，最多 3 字节，存不了 emoji 和部分生僻字（4 字节）。`utf8mb4` 才是完整 UTF-8。
</details>

**A3. `(status, published_at)` 联合索引，能加速 `WHERE published_at > '2026-01-01'` 吗？**
<details><summary>答案</summary>
不能。联合索引按字段顺序排序（像电话簿先按姓再按名），跳过了最左列 `status` 就用不上。`EXPLAIN` 里 `key` 会是 NULL。这就是「最左前缀原则」。
</details>

**A4. 为什么查询用 `SELECT *` 不好？**
<details><summary>答案</summary>
1) 传了没用的字段（如 `longtext` 正文），浪费带宽和内存；2) 可能用不上覆盖索引；3) 表结构一变，JSON 输出可能意外多出字段（`password_hash` 就是这样泄漏的）。
</details>

**A5. 软删除和硬删除的取舍？**
<details><summary>答案</summary>
软删除（`UPDATE deleted_at`）：能恢复、能审计、关联数据保留；代价是数据累积、每次查询都要过滤。硬删除（`DELETE`）：干净，但不可恢复。后台管理类系统一般用软删除。
</details>

**A6. 事务里为什么要传 `tx` 而不是继续用 `s.db`？**
<details><summary>答案</summary>
`s.db` 是独立的连接，不在事务里。用它写的操作不会随事务回滚，会造成「一半提交一半回滚」的不一致。
</details>

**A7. `view_count = view_count + 1` 为什么不能写成「先查出来 +1 再存」？**
<details><summary>答案</summary>
并发下两个请求可能都读到 100，各自 +1 写回 101，实际应该是 102 —— 丢更新。用 SQL 表达式让数据库内部原子完成。
</details>

**A8. 分类为什么不能直接删除？标签为什么可以？**
<details><summary>答案</summary>
文章表存了 `category_id`，删分类会让文章指向不存在的分类（引用完整性问题），所以先检查该分类下有没有文章，有就拒绝。标签是多对多，删标签只影响 `article_tags` 关联（能清理干净），不影响文章内容本身。
</details>

## B. Go 与 Gin（10 题）

**B1. HTTP 状态码和业务 code 为什么要有两套？**
<details><summary>答案</summary>
HTTP 状态码只有几十个，且语义面向「传输层」；业务错误（用户名已存在、token 过期、无权限）都需要 4xx/5xx 细分，前端要区别对待（401 跳登录、403 提示无权限、409 提示冲突）。两套并存：网关看 HTTP 码，前端看业务码。
</details>

**B2. 中间件里 `c.Next()` 前后的代码分别什么时候执行？**
<details><summary>答案</summary>
`c.Next()` 之前：请求刚进来，还没到业务；`c.Next()` 之后：所有内层 handler 执行完、响应写完。所以日志要写在 `c.Next()` 之后才能拿到真实状态码和耗时。
</details>

**B3. 鉴权中间件为什么必须 `c.Abort()`？**
<details><summary>答案</summary>
`c.Abort()` 阻止后续 handler 执行。少了它，即使已经写出 401 响应，业务 handler 仍会执行 —— 攻击者没 token 也能触发写操作（权限绕过）。
</details>

**B4. `gin.New()` 和 `gin.Default()` 有什么区别？**
<details><summary>答案</summary>
`Default()` = `New()` + Logger + Recovery 中间件。我们自己实现了 Logger/Recovery，用 `Default()` 会重复，所以用 `New()`。
</details>

**B5. 为什么 handler 里不能直接写 SQL？**
<details><summary>答案</summary>
三个理由：1) 同一份业务逻辑没法在别的入口（定时任务、命令行）复用；2) 没法单测（要起 HTTP）；3) 职责混乱，改查询容易碰坏参数解析。
</details>

**B6. service 返回的错误，handler 怎么知道该返回 400 还是 404？**
<details><summary>答案</summary>
用哨兵错误 + `errors.Is`：service 返回 `ErrNotFound` / `ErrInvalidInput` / `ErrConflict` / `ErrUnauthorized`，handler 的 `fail()` 统一翻译成对应状态码。没包装的普通错误一律 500 且只返回笼统消息。
</details>

**B7. 为什么 500 错误不能把原始错误信息返回给前端？**
<details><summary>答案</summary>
数据库错误的原文常带表名、列名、SQL 片段甚至连接信息，等于给攻击者送地图。做法：完整错误写日志，对外只给「服务器内部错误」。
</details>

**B8. 优雅关闭的顺序为什么不能颠倒？**
<details><summary>答案</summary>
必须先 `srv.Shutdown()` 停止接收新请求并等待进行中的请求完成，**然后**才关数据库连接池。反过来的话，还在执行的 handler 会撞上已关闭的连接池，报 `sql: database is closed`。
</details>

**B9. 为什么 `gorm.Open()` 之后还要 `Ping()`？**
<details><summary>答案</summary>
`gorm.Open` 是惰性的，只创建对象不真正连接。不 Ping 的话服务会「启动成功」，直到第一个请求才炸——错误暴露得越晚越难排查。
</details>

**B10. 启动时为什么要校验配置必填项？**
<details><summary>答案</summary>
配置错了应该 0.1 秒内退出并明确报错。等到第一次查询才发现，服务已经对负载均衡报了「健康」，流量进来了才报错，排查成本高。而且退出码非 0，容器编排才知道要重启。
</details>

## C. 认证与安全（9 题）

**C1. 为什么密码不能明文存数据库？**
<details><summary>答案</summary>
一旦拖库（SQL 注入、备份外流、内部人员、误连生产），所有密码全裸。用户常在多个网站用同一密码，会连累他的一切账号。
</details>

**C2. 为什么不用 MD5 / SHA256 存密码？**
<details><summary>答案</summary>
它们的设计目标是「快」，GPU 每秒能算几十亿次，配合彩虹表能反查常见密码。bcrypt 故意慢（cost=10 约 60ms/次），且有随机盐，彩虹表失效。
</details>

**C3. 同一个密码两次 bcrypt 结果不同，为什么校验还能通过？**
<details><summary>答案</summary>
每次生成都会随机一个 salt 并混进结果。校验时从哈希里取出 salt，用同样成本重算再比较。随机盐让预计算的彩虹表无法复用。
</details>

**C4. JWT 的 payload 是加密的吗？能放什么？**
<details><summary>答案</summary>
不是加密，只是 Base64 编码，任何人可解。只能放非敏感信息（user_id、用户名、角色）。绝不能放密码、手机号、身份证。
</details>

**C5. JWT 凭什么防篡改？**
<details><summary>答案</summary>
`Signature = HMAC-SHA256(header.payload, SECRET)`。改了 payload 任何字符，签名就对不上，验签失败。注意：防的是篡改，不是防「看」。
</details>

**C6. `JWT_SECRET` 泄漏会发生什么？**
<details><summary>答案</summary>
攻击者可以给任意用户（包括 admin）签发合法 token，等于拿到全站最高权限。所以密钥只放 `.env` 不进 Git；更换密钥 = 所有已发 token 立即失效（强制全员重新登录的唯一手段）。
</details>

**C7. 什么是 alg 混淆攻击？怎么防？**
<details><summary>答案</summary>
把 JWT header 里的 `alg` 改成 `none`，让服务端「跳过验签」。防法：解析时限定算法 `WithValidMethods([]string{"HS256"})`。项目里有测试 `TestParseRejectsNoneAlgorithm` 守着。
</details>

**C8. 为什么登录失败统一提示「用户名或密码错误」？**
<details><summary>答案</summary>
如果区分「用户不存在」和「密码错误」，攻击者就能批量探测哪些账号真实存在（用户名枚举），再针对性地爆破。
</details>

**C9. 上传接口为什么要看文件内容而不是扩展名？**
<details><summary>答案</summary>
扩展名完全由用户控制：`shell.php` 改名成 `logo.png` 就能绕过。必须读文件头（`http.DetectContentType`）判断真实 MIME，白名单只放行图片类型。另外文件名要服务端随机生成，避免路径穿越。
</details>

## D. 前端（8 题）

**D1. 为什么用 Vite 代理而不是让后端开 CORS？**
<details><summary>答案</summary>
生产环境一定是 Nginx 把 `/api` 转发到后端，开发期用 Vite 代理是同一个形态。这样前端代码里没有任何环境相关的地址，上线零改动。CORS 只是备选方案（而且配错很容易出安全问题）。
</details>

**D2. 响应拦截器直接返回 `data`，页面里怎么拿业务数据？**
<details><summary>答案</summary>
后端统一返回 `{code, message, data}`，拦截器判断 `code===0` 后 `return body.data`。所以 `const data = await fetchArticles()` 拿到的就是 `data` 部分，`data.list` 就是列表。
</details>

**D3. `v-html` 有什么风险？怎么防？**
<details><summary>答案</summary>
`v-html` 把字符串当 HTML 执行，可注入 `<script>` 或 `<img onerror=...>` 偷 token。必须用 DOMPurify 净化（项目里 `renderMarkdown` 已内置）。
</details>

**D4. 路由守卫能保证接口安全吗？**
<details><summary>答案</summary>
不能。前端守卫只是体验优化，用户改 localStorage 就能绕过。真正的安全在后端每个接口校验 token 与角色。
</details>

**D5. 切换筛选条件后为什么要 `page.value = 1`？**
<details><summary>答案</summary>
否则会带着原来的页码去查新条件。比如在第 5 页筛选一个只有 3 条的分类，会得到空列表，用户以为「没有数据」。
</details>

**D6. 为什么 `loading` 要在 `finally` 里关？**
<details><summary>答案</summary>
请求失败（抛异常）时如果只写在 try 末尾，`loading` 会一直是 true，页面永远转圈。`finally` 保证无论成功失败都执行。
</details>

**D7. 打包出来 830KB 怎么优化？**
<details><summary>答案</summary>
Element Plus 全量引入导致。用 `unplugin-vue-components` + `unplugin-auto-import` 做按需引入，配合路由懒加载，主包能降到 200KB 以内。另外注意别全量 import highlight.js（1MB→143KB）。
</details>

**D8. 生产环境刷新 `/article/1` 返回 404 是什么原因？**
<details><summary>答案</summary>
history 模式的 SPA 需要服务端把所有路径回退到 `index.html`。Nginx 要配 `try_files $uri $uri/ /index.html;`。
</details>

## E. 综合排查（5 题）

**E1. 前端调接口返回 500，你怎么定位？**
<details><summary>答案</summary>
1) 看后端日志的 `[ERROR]` 行（我们只对 500 打详细日志）；2) 复制请求用 curl 打一遍确认可复现；3) 打开 GORM dev 模式看实际 SQL；4) 直接去数据库跑那条 SQL 看结果。
</details>

**E2. 列表接口返回 total=10 但 list 只有 3 条，可能什么原因？**
<details><summary>答案</summary>
`Count` 和 `Find` 用的查询条件不一致。最常见是 GORM 链式对象复用了同一个 `*gorm.DB`（条件叠加/丢失）。我们项目里用 `base()` 函数每次返回新对象来规避。
</details>

**E3. 改了代码但页面/接口行为没变，第一反应查什么？**
<details><summary>答案</summary>
接口：端口是否被旧进程占用（`lsof -nP -iTCP:8090 -sTCP:LISTEN`），启动日志里有没有 `bind: address already in use`。页面：是否看的是旧标签页 / HMR 是否还活着。
</details>

**E4. 中文变乱码，三层字符集是指哪三层？**
<details><summary>答案</summary>
1) 服务端默认 `character_set_server`；2) 库/表 `CHARSET=utf8mb4`；3) **客户端连接** `character_set_client`（最容易漏，`~/.my.cnf` 或 `--default-character-set=utf8mb4`）。三层必须一致。
</details>

**E5. 用户报「评论提交了但看不到」，你怎么解释？**
<details><summary>答案</summary>
不是 bug，是设计：新评论默认 `status=0` 待审核，前台只展示 `status=1`。需要管理员在 `/admin/comments` 通过后才可见。这也是为什么接口返回的 message 特意写了「等待管理员审核后展示」。
</details>
