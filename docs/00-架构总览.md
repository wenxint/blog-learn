## 1. 一句话架构

```
浏览器 → Vue3 SPA → Axios → Vite/Nginx 代理 → Gin(4 层中间件) → handler → service → repository → GORM → MySQL
```

前后端完全分离：后端只返回 JSON，前端负责渲染。开发期前端跑 5173、后端跑 8090，靠代理连起来。

## 3. 请求链路

以「文章列表」为例：

```
1. 页面 GET /api/v1/articles?page=1&page_size=10
2. Vite proxy 转发到 http://127.0.0.1:8090（生产期是 Nginx）
3. Gin 中间件链：
     RequestID  生成/沿用 X-Request-Id，写进 Context
     Logger     记录开始时间，c.Next() 之后打印状态码与耗时
     Recovery   兜住 panic，返回统一 500 JSON
     CORS       设置跨域头；OPTIONS 预检直接 204 返回
4. 路由匹配 → ArticleHandler.List
5. ShouldBindQuery 绑定 + 校验（pagination.Query 负责默认值与上限）
6. 调 ArticleService.List
7. 组装 ArticleFilter，调 ArticleRepository.List
8. Repository 用 GORM 查：Count + Find（含 Preload 3 张关联表）
9. 逐层返回，Handler 用 response.OK(c, pagination.NewResult(...)) 输出
10. 前端 Axios 响应拦截器判断 code===0，直接返回 data 给页面
```

**为什么这个顺序重要**：`RequestID` 必须最外层（内层要读它写的值），`Logger` 必须在 `c.Next()` 后打印（才能拿到真实状态码），`Recovery` 必须包住业务（才能接住 panic）。

## 5. 分层规则（写代码时的铁律）

```
handler ──► service ──► repository ──► gorm ──► MySQL
   │           │            │
   └─── 共用 ──► model / pkg
```

| 规则 | 说明 |
|---|---|
| 只允许向下调用 | handler 不直接调 repository；service 不写 SQL 细节 |
| 不允许反向依赖 | repository 不 import service（否则编译不过） |
| 依赖注入 | `NewXxxHandler(svc)`，装配集中在 `router.New()`，不用全局变量 |
| 错误语义 | service 返回 `ErrNotFound/ErrInvalidInput/ErrConflict/ErrUnauthorized`，handler 的 `fail()` 翻译成状态码 |
| 不泄漏内部信息 | 500 只回笼统消息，细节进日志 |

**为什么：** 改一处不炸一片、能单测、能换实现（同一份 service 可以给 gRPC / 定时任务复用）。

## 6. 数据模型（6 张表 / 49 个字段）

| 表 | 字段数 | 说明 |
|---|---|---|
| `users` | 10 | 用户，`password_hash` 为 bcrypt（60 字符） |
| `categories` | 7 | 分类，`name`/`slug` 唯一 |
| `tags` | 5 | 标签，`name`/`slug` 唯一 |
| `articles` | 15 | 文章，含 `deleted_at` 软删除、`published_at` 可空 |
| `article_tags` | 2 | 多对多关联，联合主键 `(article_id, tag_id)` |
| `comments` | 10 | 评论，`parent_id=0` 为一级评论（最多两级） |

**索引**

```sql
articles:  PRIMARY(id)
           idx_status_published (status, published_at)   -- 服务「已发布 + 按时间倒序」
           idx_category (category_id)
           idx_author (author_id)
users:     uk_username
categories:uk_name, uk_slug
tags:      uk_name, uk_slug
comments:  idx_article, idx_status
```

**为什么索引顺序是 `(status, published_at)`**：查询是 `WHERE status=1 ORDER BY published_at DESC`，等值条件在前、排序字段在后，MySQL 能沿索引反向扫描，`Extra` 里没有 `Using filesort`。

## 8. 统一响应与错误码

```json
{ "code": 0, "message": "ok", "data": {} }
```

| code | HTTP | 含义 | 前端动作 |
|---|---|---|---|
| 0 | 200 | 成功 | — |
| 10001 | 400 | 参数错误 | 提示具体原因 |
| 10002 | 401 | 未登录 / token 无效 | 清 token 跳登录 |
| 10003 | 403 | 无权限 | 提示无权限 |
| 10004 | 404 | 资源不存在 | 提示不存在 |
| 10005 | 409 | 冲突（重名、有文章的分类） | 提示冲突原因 |
| 10006 | 500 | 服务器内部错误 | 提示稍后重试，细节看日志 |
| 10007 | 429 | 请求过于频繁（评论限流） | 提示「请 N 秒后再试」 |

**分页返回**

```json
{ "code":0, "data": { "list": [], "total": 42, "page": 1, "page_size": 20 } }
```

`page_size` 默认 20、上限 100，规则只在 `pkg/pagination` 里写一次。

## 9. 认证方案

```
注册 → bcrypt 哈希（cost=10）存 password_hash
登录 → 校验密码 → 签发 JWT（HS256，24h）
请求 → Authorization: Bearer <token> → 中间件验签 → 用户信息放进 Context
```

**JWT payload**：`user_id` / `username` / `role` / `iss=blog` / `exp`
（payload 只是 Base64，**不是加密**，所以不放敏感信息）

**安全要点**
- 密钥只在 `.env`，不进 Git；更换 = 全员重新登录
- 限定算法 HS256（防 alg 混淆攻击）
- 登录失败统一提示（防用户名枚举）
- 身份只从 token 取，不信前端传的 `author_id`
- 401 = 未认证（跳登录），403 = 已认证但无权限

## 12. 已知限制 / 待优化

| 项 | 现状 | 建议 |
|---|---|---|
| 前端包体积 | ✅ 已按需引入：JS/CSS 1.7MB→1.0MB，最大包 830KB→141KB（图片资源另计） | 进一步可用 CDN / gzip+brotli |
| 评论限流 | ✅ 已实现滑动窗口（默认 3 条/60 秒，超出 429） | 多实例部署时换 Redis |
| 分类/标签缓存 | 每次都查库 | 数据变化少，可加 5 分钟内存缓存或 Redis |
| 限流状态在内存 | 进程重启清零，多实例不共享 | 换 Redis `INCR + EXPIRE` |
| 文章正文搜索 | `LIKE '%kw%'`（索引失效） | 数据量大时改全文索引或 Meilisearch |
| 上传存储 | 本地磁盘 | 生产建议对象存储 + CDN |
| 单元测试 | 覆盖 config / hash / jwt / ratelimit（24 个） | service 层需要 mock repository，可后续补 |
| 归档按月筛选 | `DATE_FORMAT` 导致索引失效 | 改成 `published_at >= ? AND < ?` |
