上线那天的预期是：传二进制、配 Nginx、起服务，半小时收工。

实际从 15:36 折腾到 17:40。中间我重启过两次服务、改了三版 Nginx，最后发现**根因根本不在应用层**——域名被注册商置成了 `clientHold`，注册局不发布 NS 委派，解析器在 `.xyz` 这一层就直接返回 NXDOMAIN。

这篇不复述命令，讲两件事：那天的时间线，以及「按层排障」到底是怎么做的。

## 排障顺序：从外到内，还是从内到外

出问题时最危险的动作是「先重启一下试试」。重启会改变现场，让本来能定位的问题变得不可复现。

那天的顺序是**从外到内**：

```
域名/DNS → 网络/安全组 → Nginx/端口 → Go 进程 → 数据库/编码
```

每层都有一个「不依赖下一层」的验证方法：

| 层 | 验证命令 | 说明 |
|---|---|---|
| 域名 | `dig +short youzhichong.xyz` | 没记录就是域名侧的问题，先别碰服务器 |
| 权威/注册状态 | RDAP 查询 | 能看到 `clientHold`、NS 是否委派 |
| 网络 | `nc -vz IP 8080` | 端口不通可能是安全组 |
| Nginx | `curl -I http://127.0.0.1:8080` | 本机通、外网不通 → 网络层 |
| 应用 | `curl http://127.0.0.1:8090/api/v1/ping` | Nginx 通、反代 502 → 后端 |
| 数据库 | `/debug/db`、`journalctl` | 应用活着但 500 → 查 DB/日志 |

那天如果先做这张表，15:40 查到「没有 A 记录」时就该停在域名层，而不是继续改 Nginx。**「域名没解析」和「服务没起来」的表现都是打不开，但修复动作完全相反。**

## 根因：clientHold 不是 DNS 配置错误

在 DNS 面板里加 A 记录、换 NS、清缓存——这些都没用，因为问题不在我的配置。

`clientHold` 是注册商给域名设的状态，意思是「暂停发布」。注册局看到这个状态，就不会把域名的 NS 委派写进 `.xyz` 顶级域。递归解析器查不到委派，只能返回 NXDOMAIN。

用 RDAP 能直接看到状态：

```bash
curl -s "https://rdap.verisign.com/xyz/v1/domain/youzhichong.xyz" \
  | python3 -m json.tool | grep -A5 status
```

解决方式不是技术操作：完成实名认证，等注册商解除。解除后还有第二个坑——**DNS 负缓存**。

递归解析器会把「查不到」的结果缓存一段时间（通常几分钟到几十分钟）。所以注册局 17:10 解除后，17:39 才全球生效，中间 29 分钟不是「没生效」，是缓存在等过期。

这段经历的直接教训：**域名问题先查注册状态，再查解析记录。** 面板里「NS 不一致」的警告是线索，不是结论。

## 另外三个不是域名的坑

### 交叉编译：Mac 上编出来的不能直接在 Linux 跑

第一次 `make build` 的产物传上去，执行报 `cannot execute binary file`。因为默认编译目标是当前系统（darwin/arm64）。

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 make build
```

`CGO_ENABLED=0` 是为了产出纯静态二进制，不依赖服务器的 glibc 版本。验证方式是看文件本身：

```bash
file bin/blog-server
# ELF 64-bit LSB executable, x86-64, statically linked
```

### `.env.prod` 没被 gitignore 保护

生成生产配置后，`git check-ignore` 提示未被忽略。如果当时执行 `git add -A`，密钥就进仓库了。

修复是把它加进 `.gitignore`，并且今后每次新增环境文件都先跑一遍：

```bash
git check-ignore -v backend/.env.prod
```

同时 `config.go` 原来只认 `.env` 这个文件名，生产要用 `.env.prod`，于是加了 `ENV_FILE` 支持。这类改动很小，但它决定了「同一份代码能不能在两种环境里用同一套启动逻辑」。

不是数据库、不是表、不是后端——是 **mysql 命令行客户端**。服务器和 CI 环境里 `LANG` 经常为空，客户端默认用 latin1，UTF-8 文件被当成 latin1 读入再以 utf8mb4 存库，等于编码了两次。

修复是导入时显式指定：

```bash
mysql -ublog -p --default-character-set=utf8mb4 blog < migrations/002_seed.sql
```

排查时看字节最直接：

```bash
mysql -ublog -p blog -e "SELECT HEX(title) FROM articles LIMIT 1"
# 正常中文「从」是 E4BB8E；如果变成 C3A4C2BB... 就是双重编码
```

## 这次上线验证到什么程度

- 本地：前后端启动、接口、页面、中文都正常
- 服务器：systemd `active`，以 `blog` 用户运行，5 个迁移全部执行
- 公网：`http://youzhichong.xyz:8080` 返回 200，标题正确
- **未完成**：备案、HTTPS、监控、备份自动化

我把「未完成」写在这里，是因为上线不是一次性的动作。**能打开只是起点，能长期稳定运行才是目标。**

## 复盘：如果重来一次

1. **先画排障层级表**，再动手。域名、网络、代理、应用、数据库，每层一个独立验证命令。
2. **不要先重启**。重启前先抓日志和状态，现场比「再试一次」值钱。
3. **部署脚本要能重复跑**。`build.sh` 里的交叉编译参数、`ENV_FILE` 支持、字符集参数，都应该固化进脚本，而不是靠记忆敲。
4. **上线清单要逐条打勾**。第 11 篇那十条检查，这次只做了六条，剩下的（HTTPS、备份、监控）就成了遗留项。
