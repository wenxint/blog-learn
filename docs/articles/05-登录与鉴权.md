登录功能写在纸面上只有三步：验密码、发令牌、下次带着令牌来。

但真正写的时候，问题全在细节里：密码用什么存？令牌被改了怎么办？用户改了密码，旧令牌还能不能用？前端把令牌放哪？后端怎么知道「你是谁」而不是「你说你是谁」？

这篇把这几个问题拆开讲。它对应学习路线的第 8～10 课，代码在 `pkg/hash`、`pkg/jwt`、`middleware/jwt_auth.go` 和 `service/auth_service.go`。

## 密码不能用 MD5 存，也不能用 SHA 存

先说最容易被糊弄过去的一条：数据库里不能有明文密码。

原因不是「不安全」三个字，而是**泄漏的形态**。数据库被拖、备份文件外流、开发机误连了生产库——只要发生过一次，所有用户的密码就是可读的。而用户往往在多个网站用同一个密码，一次泄漏会连累他在别处的账号。

那用 MD5 或 SHA-256 哈希一下行不行？不行。这两个算法是**为「快」设计的**：校验文件完整性时，快是优点。但存密码时，快意味着攻击者也能算得飞快。一块普通 GPU 每秒可以尝试几十亿次常见密码组合，加上彩虹表，弱密码几乎等于明文。

bcrypt 反过来：它**故意慢**。

```go
// backend/internal/pkg/hash/password.go
const cost = 10   // 单次约 50~80ms，每 +1 耗时翻倍

func Password(plain string) (string, error) {
    if len(plain) > MaxPasswordLen {
        return "", fmt.Errorf("密码长度不能超过 %d 字节", MaxPasswordLen)
    }
    b, err := bcrypt.GenerateFromPassword([]byte(plain), cost)
    return string(b), err
}
```

![MD5 快在「算得快」，bcrypt 慢在「让攻击者也不得不慢」，两者的设计目标正好相反](/diagrams/bcrypt-cost.svg)

慢带来两个直接好处：

1. **爆破成本被放大**。攻击者每猜一次都要付 60ms，10 亿次就是 6 亿秒。这个成本高到不值得，防线就成立了。
2. **内置随机盐**。同一个密码两次哈希，结果完全不同，但两次都能验通过。彩虹表预先算好的哈希对不上任何一条记录。

代价也很明确：登录接口每次多花几十毫秒。用户能感知到，但可以接受——**用可接受的延迟，换不可接受的爆破成本**，这笔账是划算的。

还有一个坑：**bcrypt 只取输入的前 72 字节**，超出的部分被静默忽略。如果不拦，两个前 72 字节相同的不同密码可以互相登录。所以 `MaxPasswordLen = 72`，注册、改密码两个入口都显式校验。

## JWT 能防篡改，但不能保密

登录成功后，服务端发一个 JWT。它的结构是三段 Base64，用点连接：

```
header.payload.signature
```

很多人第一次看到「三段乱码」，会以为它是加密的。不是。**payload 只是 Base64 编码，任何人复制出来都能解开看**。所以里面只能放非敏感信息：

```go
type Claims struct {
    UserID   uint64 `json:"user_id"`
    Username string `json:"username"`
    Role     string `json:"role"`
    jwtlib.RegisteredClaims   // iss / sub / iat / nbf / exp
}
```

那它凭什么可信？凭第三段签名。服务端用密钥对前两段做 HMAC，任何改过 payload 的令牌，签名都对不上：

```
改一个字节的 user_id → 签名校验失败 → 401
```

这就是「防篡改」的全部原理。它不是把内容藏起来，而是**内容动过就过不了校验**。

![登录签发令牌、之后每次请求验签：JWT 只传递身份，服务端不保存会话](/diagrams/jwt-flow.svg)

这里有一个必须写对的地方：验签时要**限定算法**。

```go
jwtlib.WithValidMethods([]string{jwtlib.SigningMethodHS256.Alg()})
```

如果不限定，攻击者可以把 header 里的 `alg` 改成 `none`，构造一个「不需要密钥也能通过」的令牌；或者换成别的算法族做混淆。这类问题统称 alg 混淆攻击。项目里还额外做了一次类型断言，双重确认必须是 HMAC。

密钥本身只在 `.env` 里，不进 Git。它的重要性怎么强调都不过分：**拿到密钥的人可以伪造任何人的身份**。换密钥的副作用也很直接——所有已发出的令牌全部失效，等于全员重新登录。

## 中间件只做两件事

请求到后端后，先过鉴权中间件。它只做两件事：验签、把身份写进 Context。

```go
// backend/internal/middleware/jwt_auth.go
claims, err := mgr.Parse(token)
if err != nil {
    response.Unauthorized(c, err.Error())
    c.Abort()          // 关键：不 Abort 会继续进业务 handler
    return
}
authctx.Set(c, claims.UserID, claims.Username, claims.Role)
c.Next()
```

`c.Abort()` 是新手最容易漏的一行。漏了会怎样？校验失败已经写了 401 响应，但函数继续往下走，业务 handler 照样执行——**鉴权被绕过**。这类问题不会报错，只会安静地放行。

身份信息只从令牌里取，绝不信任前端传的 `author_id`。后台创建文章时，请求体里就算带了 `author_id`，Service 也会用 `authctx.UserID(c)` 覆盖掉。前端传的一切都视为不可信，这是条底线。

401 和 403 的区别也在这里定死：

| 状态码 | 含义 | 前端动作 |
|---|---|---|
| 401 | 我不知道你是谁（没带、过期、伪造） | 清登录态，跳登录页 |
| 403 | 我知道你是谁，但你没这个权限 | 提示「没有权限」，不跳转 |

角色判断单独一个中间件：

```go
func AdminOnly() gin.HandlerFunc {
    return func(c *gin.Context) {
        if authctx.Role(c) != "admin" {
            response.Forbidden(c, "需要管理员权限")
            c.Abort()
            return
        }
        c.Next()
    }
}
```

挂的时候**整组挂**，而不是逐个接口加：`admin.Use(middleware.AuthRequired(jwtMgr), middleware.AdminOnly())`。这样以后新增接口，不会因为忘了加鉴权而裸奔。

## 前端那半边：令牌放哪，什么时候清

前端把 token 存在 `localStorage`，请求拦截器自动加头：

```js
// frontend/src/api/request.js
request.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

放 `localStorage` 而不是内存，是为了刷新页面后还保持登录。代价是**能被 XSS 偷走**——这也是为什么正文渲染必须过 DOMPurify（第 09 篇会讲）。

响应拦截器里，401 统一清登录态并提示重新登录；403 只提示无权限。

这里有一个真实踩过的坑：最初的实现里，**网络抖动也会把用户踢下线**。后端重启、请求超时、手机切换网络，都会走进错误分支，然后清掉 token。表现就是「用着用着突然要重新登录」。

修复很简单：只有**明确的 401** 才清登录态，其它错误只提示、不清 token。

```js
// stores/user.js
if (err?.response?.status === 401) {
  logout()
}
```

判断依据必须是「服务端明确说未授权」，而不是「这次请求失败了」。

## 这笔债：JWT 装不下「立刻踢人」

JWT 是**无状态**的：服务端不保存会话，只验签名。好处是横向扩展容易，坏处是——**令牌一旦发出，到期之前无法撤销**。

具体表现为：

- 用户改了密码，旧令牌仍然有效，直到 24 小时后过期
- 管理员封了号，被封的人只要还拿着未过期的令牌，依然能操作
- 用户觉得「在别的设备上退出登录」，其实只是删了本地的 token

要解决就得回到有状态：维护一个黑名单（Redis 存 `jti`），或者给用户表加 `token_version`，每次校验多查一次。**只要开始存状态，无状态的好处就打折了**。这是 JWT 最真实的取舍，不是「会不会用」的问题。

我目前的处理是：接受 24 小时的窗口，敏感操作（改密码）要求重新验证原密码。等真的有多实例和高安全需求，再上黑名单。
