表结构是最不该省事的地方。接口写错了可以改，表结构一旦有数据，改起来就要迁移、备份、停机窗口。

这套博客只有六张表，但我为每一列都想清楚了"为什么它在"。

## 全景

![数据模型](/diagrams/er.svg)

## 索引顺序：等值在前，排序在后

六张表里最值得说的是 `articles`。它的列表查询是：

```sql
SELECT ... FROM articles
WHERE status = 1
ORDER BY published_at DESC
LIMIT 10;
```

为它建的索引是 `(status, published_at)`——等值条件在前，排序字段在后。这样 MySQL 能先定位到 `status = 1`，再沿叶子链表反向读出已排序的 10 条，`EXPLAIN` 里没有 `Using filesort`。

如果反过来写成 `(published_at, status)`，树是按时间排的，MySQL 只能按时间逐条扫、过滤草稿，凑够 10 条之前不知道要读多少行。

![同样的两列，顺序不同：一个能边扫边出有序结果，一个必须把结果取出来再排序](/diagrams/index-order.svg)

这就是联合索引的「最左前缀」：第一列决定能不能快速定位，后面的列决定能不能顺便排序。建索引前先把查询拆成「等值 / 排序 / 范围」三类，顺序自然就出来了。索引失效的两个场景（`DATE_FORMAT` 和前置通配符 `LIKE`）在后面「已知会变慢的地方」里讲。


## 七个决定

### 一、文章不做"多分类"，只做一个

`articles.category_id` 是单值。为什么不是多对多？

因为博客的分类是**导航维度**——读者点"技术笔记"是想看这一类，不是想同时看到"技术笔记 + 生活随笔"。多分类的代价是查询要 join 中间表、筛选逻辑变复杂，而收益几乎为零。

标签才是多维度，所以 `article_tags` 是真正的多对多。

### 二、article_tags 没有自增 id

```sql
CREATE TABLE article_tags (
  article_id BIGINT UNSIGNED NOT NULL,
  tag_id     BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (article_id, tag_id)
);
```

联合主键直接保证了"同一篇文章不会重复挂同一个标签"，省掉一次应用层去重。如果加个自增 id，就得再建一个唯一索引 `(article_id, tag_id)`，多一份存储和一次检查。

**中间表的价值在唯一性，不在可寻址性**——没有任何地方需要"按 id 引用一条关联记录"。

### 三、评论用 parent_id，但只做两层

评论树可以无限嵌套。我只做了两层（评论 + 回复），`parent_id = 0` 表示顶层。

为什么不多层？因为**三层以上的嵌套在 UI 上没法看**——手机上缩进三次就只剩一半宽度。大多数博客（包括 WordPress 主题）最终都会在视觉上压平，那不如在数据层就限制住。

查询时只需要两次：

```sql
-- 顶层评论
SELECT * FROM comments WHERE article_id = ? AND parent_id = 0 AND status = 1;

-- 所有回复（一次取回，应用层按 parent_id 组装）
SELECT * FROM comments WHERE article_id = ? AND parent_id <> 0 AND status = 1;
```

### 四、软删除用 deleted_at，但每个查询都要记得它

文章删除是软删：`deleted_at` 有值表示已删。

这样做的代价是**每一个查询都必须记得带上 `deleted_at IS NULL`**，漏一个就会查出已删的文章。所以查询全部收在 Repository 里，`Delete` 之外没有任何地方直接拼条件。

GORM 的软删除会自动加这个条件。关键索引长这样：

```sql
CREATE INDEX idx_articles_status_published
  ON articles (status, published_at);
```

`status = 1 AND deleted_at IS NULL ORDER BY published_at DESC` 这条查询，能用上 `(status, published_at)` 做等值定位 + 有序读取，`EXPLAIN` 里 `Extra` 没有 `Using filesort`；`deleted_at IS NULL` 作为回表后的残余条件过滤，在当前数据量下影响可以忽略。如果将来软删除的数据占比很高，再考虑把 `deleted_at` 放进索引。

如果索引只建在 `status` 上，MySQL 还得对结果排序，数据量一大就慢。

### 五、不用物理外键

```sql
-- 有这行
category_id BIGINT UNSIGNED NOT NULL,
-- 没有这行
-- FOREIGN KEY (category_id) REFERENCES categories(id)
```

这是最有争议的一个决定。不用外键的理由：

1. **迁移会变麻烦**。要改表结构时，外键的依赖顺序会限制操作。
2. **批量操作会变慢**。每次写入都要检查父表。
3. **完整性可以在 Service 层保证**。创建文章时先校验分类存在，这是业务逻辑的一部分。

代价也很明确：**数据库层面不再保证一致性**。如果绕过 Service 直接写 SQL（比如手动修数据），可能写进一个不存在的 category_id。

我的做法是：**所有写操作都走 Service，不给"直接写库"留口子**。这是一个约定，不是数据库强制的约束。

> 如果是多人协作、有 DBA、或者数据一致性要求高（金额、库存），我会用外键。这个博客的数据丢了也能重建，所以选了灵活。

### 六、view_count 直接 UPDATE，不防并发

文章详情每次访问 `view_count = view_count + 1`。

并发下这会丢计数吗？会。但丢的是阅读数，不是订单金额。为此加锁或改成异步队列，复杂度远超收益。

**不是所有不一致都值得修**——要按数据的重要性分级。

### 七、Preload 是 1 + 3 条查询，不是 1 + N

文章列表要同时带分类、作者、标签。如果遍历文章逐个查关联，就是 N+1：1 条主查询 + 每篇 3 条。

GORM 的 `Preload` 把关联查询压成固定次数：

```go
r.build(f).
    Preload("Category").
    Preload("Author").
    Preload("Tags").
    Limit(f.PageSize).
    Find(&list)
```

实际发出 4 条 SQL：主查询、分类、作者、标签。文章有 20 篇还是 200 篇，都是 4 条。

![Preload 把 N 次关联查询压成固定 3 次，查询总数与列表长度无关](/diagrams/gorm-query.svg)

代价是 `Preload` 发的是额外查询，不是 join。数据量小时，4 次往返可能比 1 次 join 慢；数据量大、关联表又宽时，join 会产生重复行。选哪个要看真实耗时，不能只看「听起来更优」。


## 两个已知会变慢的地方

这两个问题我在设计时就知道，只是当前数据量下不值得优化：

### 1. 归档按 `DATE_FORMAT` 分组

```sql
SELECT DATE_FORMAT(published_at, '%Y-%m') AS month, COUNT(*)
FROM articles WHERE status = 1 GROUP BY month;
```

`DATE_FORMAT` 是函数，`published_at` 上的索引**部分失效**（要全索引扫描再计算）。

正确写法是范围查询：

```sql
WHERE published_at >= '2026-11-01' AND published_at < '2026-12-01'
```

但归档页需要"所有月份"的列表，用范围查询就得先查有哪些月份、再逐个查，反而多几次往返。数据量小的时候，一次全索引扫描（不回表）比多次往返更快。

### 2. 搜索用 `LIKE '%关键词%'`

前置通配符让 B+ 树索引完全用不上，只能全表扫。

换成全文索引或 Meilisearch 都行，但在几千篇文章的量级，全表扫一篇文章列表（只扫 title 一列）也就是几十毫秒。

**优化要看真实耗时，不是看"看起来慢不慢"**。`EXPLAIN` 显示 `type: ALL` 不等于线上会卡。

## 迁移文件永久冻结

`migrations/` 下的 SQL 文件按编号递增，**执行过的文件不再修改**。

这条规则看起来死板，但它解决了一个真实问题：回滚。

如果允许改历史迁移文件，那么"服务器上跑的到底是哪个版本的表结构"就说不清了。冻结之后，迁移历史就是一条只增不改的时间线，回滚代码时通常**不需要回滚表结构**——因为新代码总是兼容旧结构。

这套代码从 001 到 005，中间加过 `article_tags`、`comments` 两张表，都是新增文件，没有任何一次修改旧文件。
