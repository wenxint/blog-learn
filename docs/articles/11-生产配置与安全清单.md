「本地能跑」和「生产能跑」之间，隔着的不是一条启动命令，而是一组默认值的翻转。

开发环境为了方便，会把日志打全、把诊断接口打开、信任所有代理、用示例密码；生产环境必须把这些全部反过来。漏一项不会立刻报错，只会在某个时刻以安全事件或诡异 bug 的形式出现。

这篇把 `.env`、Nginx、systemd 里那些「dev 一套、prod 一套」的配置逐项列出来，并给出可执行的检查命令。

## 一张配置对照表

| 配置 | 开发环境 | 生产环境 | 漏配的后果 |
|---|---|---|---|
| `APP_ENV` | `dev` | `prod` | `/debug/*` 暴露，任意人可触发 panic/慢请求 |
| `TRUSTED_PROXIES` | 空 | `127.0.0.1` | 所有评论 IP 都是 127.0.0.1，限流误伤全站 |
| `JWT_SECRET` | 示例值 | `openssl rand -hex 32` | 密钥泄漏 = 任何人可伪造任意身份 |
| `DB_HOST` / 监听 | `127.0.0.1` | `127.0.0.1`（绝不 `0.0.0.0`） | 3306 暴露公网，被扫库/爆破 |
| `DB_USER` | 本地账号 | 专用最小权限账号 | 用 root 连库，一处注入拖全库 |
| 进程用户 | 当前用户 | `User=blog` | 应用被攻破 = 服务器 root 被攻破 |
| 上传上限 | 5MB | Nginx ≥ 5MB，后端 5MB | 用户传大图先被 Nginx 413，前端拿不到 JSON |
| `CORS` | 回显 Origin | 白名单 / 不需要 | 任意站点可带 cookie 调接口 |
| 日志 | 全量 | 结构化 + 轮转 | 磁盘写满或出事查不到 |

## 六道必须过的闸

### 1. 关掉调试接口

诊断接口只在 `APP_ENV != prod` 时注册：

```go
if cfg.AppEnv != "prod" {
    debug := api.Group("/debug")
    debug.GET("/db", debugHandler.DB)
    debug.GET("/panic", debugHandler.Panic)
    // ...
}
```

它不是「加个 if 隐藏」，而是**路由根本不注册**。这样即使有人猜到 URL，也只会得到统一的 404 JSON，不存在绕过的可能。

检查：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8090/api/v1/debug/db
# 生产应为 404
```

### 2. 配可信代理，否则真实 IP 全丢

Nginx 会把真实 IP 写进 `X-Real-IP` / `X-Forwarded-For`，但 Go 只采信「可信代理」带来的头：

```dotenv
TRUSTED_PROXIES=127.0.0.1
```

不配的后果不是「IP 不准」这么轻：限流按 IP 计数，所有请求都被当成 127.0.0.1，第 4 个评论的人会被提示「你发得太频繁」——而他一条都没发过。

反过来，如果配成 `0.0.0.0/0`（信任所有来源），攻击者伪造 `X-Forwarded-For` 就能绕过限流。这个值只有两种正确写法：**真实的代理地址，或者留空**。

检查：

```bash
curl -s http://127.0.0.1:8090/api/v1/admin/comments -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"ip"'
# 应看到真实公网 IP，而不是 127.0.0.1
```

### 3. 换密钥，并且让它进不了 Git

`JWT_SECRET` 是签发令牌的密钥。拿到它的人可以给任意 `user_id` / `role` 签名，服务端会认为这是合法用户。

```bash
openssl rand -hex 32   # 生成 64 位十六进制
```

它必须满足三个条件：

1. 生产与开发不同
2. 不进 Git（`.env`、`.env.prod` 都在 `.gitignore` 里）
3. 轮换时接受「全员重新登录」的代价

上线实录里发现过一次 `.gitignore` 没覆盖 `.env.prod` 的问题。这类漏洞的可怕之处是：文件本身没被提交，但 `git add -A` 时它就在暂存区里，下一次提交就带出去了。

检查：

```bash
git check-ignore -v backend/.env backend/.env.prod
# 两个都应输出匹配规则；没有任何输出就是没被忽略
```

### 4. 数据库不对外，账号最小权限

MySQL 只监听 `127.0.0.1:3306`，公网安全组不开放 3306。数据库账号只授予 `blog.*` 的权限，不用 root 连业务库。

```sql
CREATE USER 'blog'@'127.0.0.1' IDENTIFIED BY '强密码';
GRANT ALL PRIVILEGES ON blog.* TO 'blog'@'127.0.0.1';
```

`ALL PRIVILEGES ON blog.*` 已经够用。不要图省事给 `*.*`——一旦应用被注入，攻击者能拿到的就不只是博客数据。

检查：

```bash
ss -lntp | grep 3306
# 应只看到 127.0.0.1:3306，不是 0.0.0.0:3306
```

### 5. 进程不能用 root 跑

systemd 单元里：

```ini
[Service]
User=blog
Group=blog
Restart=always
EnvironmentFile=/opt/blog/backend/.env
ExecStart=/opt/blog/backend/bin/blog-server
```

如果应用以 root 运行，一个上传漏洞或命令注入就可能是整台服务器。用普通用户跑，最坏情况是「博客目录被写坏」。

同时注意 `TimeoutStopSec` 要大于程序的优雅关闭超时，否则 systemd 会在排空请求之前 `SIGKILL`。

检查：

```bash
ps -o user,pid,cmd -C blog-server
# USER 应为 blog，不是 root
```

### 6. HTTPS 与上传上限

备案通过后上证书，Nginx 监听 443 并跳转 80。上传上限两层对齐：

```nginx
client_max_body_size 8m;   # 必须 ≥ 后端的 UPLOAD_MAX_MB
```

证书续期用 certbot 的 timer，不要手动续。过期那天通常没人记得。

## 上线前逐条打勾

```bash
# 1. 环境是 prod，debug 路由不存在
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8090/api/v1/debug/db

# 2. 健康检查
curl -s http://127.0.0.1:8090/api/v1/ping

# 3. 未登录访问后台返回 401
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8090/api/v1/admin/articles

# 4. 首页与 SPA 回退
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/article/1

# 5. 静态资源缓存头
curl -sI http://127.0.0.1/assets/ | grep -i cache-control

# 6. 数据库端口
ss -lntp | grep 3306

# 7. 密钥没进 Git
git check-ignore -v backend/.env backend/.env.prod

# 8. 进程用户
ps -o user,pid,cmd -C blog-server

# 9. 备份可执行
mysqldump -ublog -p blog > /tmp/blog-$(date +%F).sql && ls -lh /tmp/blog-*.sql

# 10. 日志可查
journalctl -u blog-server -n 20 --no-pager
```

十条全部有预期输出，才算「上线完成」。**「应该没问题」不是验收标准。**

## 这笔债

这套配置能挡住常见问题，但离「生产级安全」还有距离：

- **没有密钥管理服务**：密钥在 `.env` 里，靠文件权限（600）和 gitignore 保护
- **没有 WAF / fail2ban**：暴力破解和扫描只能靠限流和日志事后发现
- **没有监控告警**：服务挂了靠人发现
- **没有备份自动化**：`mysqldump` 是手动命令，没有定时任务，也没演练过恢复
- **单机**：Nginx、Go、MySQL 挤在一台 1 vCPU 机器上，任何一次重启都是全站不可用

这些不是不知道，而是当前阶段（个人博客、单机、低流量）不值得上。但要知道边界在哪：**这套配置适合「一个人维护的小站」，不适合「有真实攻击面和经济价值的业务」。**
