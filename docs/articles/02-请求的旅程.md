打开首页时，浏览器发的第一个业务请求是：

```
GET /api/v1/articles?page=1&page_size=10
```

看起来只是"查一篇文章列表"，但在 Go 里它穿过了 4 层中间件、1 个 Handler、1 个 Service、1 个 Repository，最后变成一条带 `ORDER BY is_top DESC, published_at DESC` 的 SQL。

这篇文章把这个过程拆开。看懂这条路径，后面所有接口都是同一个模子。

## 全景

![请求时序](/diagrams/request-flow.svg)

## 第 1 层：中间件链

请求进到 Gin 之后，先过的不是业务代码，是一串中间件。顺序在 `router.New` 里写死：

```
RequestID → 日志 → Recover → CORS
```

**RequestID** 给每个请求生成一个 16 位十六进制串，塞进 `context`。后面所有日志都会带上它——线上出问题时，靠这个串能把一次请求的所有输出串起来。没有它，日志就是一堆无法关联的碎片。

**日志**记录方法、路径、状态码、耗时、客户端 IP：

```
[HTTP] d6c577f2b8ca6a1e | 200 | GET /api/v1/articles | 3.48ms | 127.0.0.1
```

耗时那一栏是排查慢接口的入口。`3.48ms` 说明数据库很快；如果突然变成 `180ms`，问题一定在 SQL 或连接池。

**Recover** 兜住 panic。Go 的 HTTP 服务里任何一个 goroutine panic 都会让整个进程退出，接口层必须有一道兜底。它做的事很简单：recover 之后返回 500，并把堆栈写进日志：

```go
defer func() {
    if err := recover(); err != nil {
        log.Printf("[PANIC] %v\n%s", err, debug.Stack())
        response.Error(c, http.StatusInternalServerError, "服务器内部错误")
    }
}()
```

**CORS** 在开发期很有用——Vite 跑在 5173，后端在 8090，浏览器认为是跨域。生产环境是同域部署（Nginx 反代），CORS 其实用不上，但也留着，因为有时候要用 Postman 或手机直连调试。

注意一个细节：**Recover 必须放在日志之后**。顺序反了的话，panic 的请求不会留下访问日志，排查时会出现"请求凭空消失"。

## 第 2 层：Handler 只做三件事

进到 `ArticleHandler.List`，它只干三件事：**绑参数、调 service、写响应**。

```go
func (h *ArticleHandler) List(c *gin.Context) {
    var q ListArticleQuery
    if err := c.ShouldBindQuery(&q); err != nil {
        response.InvalidParam(c, "参数错误: "+err.Error())
        return
    }
    q.Normalize()   // 补默认值、夹紧上限（默认 20，最多 100）

    published := service.StatusPublished
    list, total, err := h.svc.List(repository.ArticleFilter{
        Status:     &published,
        Keyword:    q.Keyword,
        CategoryID: q.CategoryID,
        TagID:      q.TagID,
        Page:       q.Page,
        PageSize:   q.PageSize,
    })
    if err != nil {
        fail(c, err, "查询文章列表失败")   // 统一错误翻译
        return
    }
    response.OK(c, pagination.NewResult(list, total, q.Query))
}
```

这里的 `ShouldBindQuery` 会顺手做校验。`page` 低于 1 会被修正成 1，`page_size` 超过 100 会被截断——**上限必须在这层挡住**，否则有人传 `page_size=100000`，一条查询就能把 1.6G 内存的服务器拖垮。

Handler 里绝对不能出现 SQL。这条规则听起来很教条，但它挡住了一类很常见的腐化：一开始"就查一个字段"，后来变三条查询，最后 Handler 里长出了业务逻辑，Service 变成空壳。

## 第 3 层：Service 管规则，不管 HTTP

Service 拿到的是一个纯数据结构，不知道 HTTP 存在：

```go
func (s *ArticleService) Detail(id uint64, onlyPublished bool) (*model.Article, error) {
    a, err := s.repo.FindByID(id)
    if err != nil {
        return nil, ErrNotFound
    }
    // 前台访问时，草稿要当成「不存在」返回 404，
    // 不能告诉调用方「有这篇，只是没发布」。
    if onlyPublished && a.Status != StatusPublished {
        return nil, ErrNotFound
    }
    // 阅读数原子 +1；失败不影响正文返回
    if err := s.repo.IncrementViewCount(id); err == nil {
        a.ViewCount++
    }
    return a, nil
}
```

它算的东西是"业务意义上的"：这篇该不该对访客可见、阅读数什么时候加、错误该翻译成「不存在」还是「无权限」。**事务边界也在这层**——比如创建文章同时要写 `article_tags`，两个操作必须在一个事务里，开事务的地方是 Service，不是 Handler 也不是 Repository。

原因：Repository 的职责是"做一次数据访问"，它不该知道"这次写入是否要和另一次写入同生共死"。事务是业务概念。

## 第 4 层：Repository 是唯一的 SQL 出口

```go
func (r *ArticleRepository) List(f ArticleFilter) ([]model.Article, int64, error) {
    var total int64
    if err := r.build(f).Count(&total).Error; err != nil {
        return nil, 0, err
    }

    var list []model.Article
    err := r.build(f).
        Preload("Category").
        Preload("Author").
        Preload("Tags").
        Order("is_top DESC, published_at DESC").
        Limit(f.PageSize).
        Offset((f.Page - 1) * f.PageSize).
        Find(&list).Error
    return list, total, err
}
```

`Preload` 会额外发三条查询（分类、作者、标签），加上主查询和 `Count`，一次列表请求固定 5 条 SQL，不是每篇文章一条。这是 `Preload` 的价值：把 N+1 压成常数。数据量大时，它也可能不如一次 join，选哪个要看真实耗时。

后台和默认列表按 `is_top DESC, published_at DESC` 排序；首页传 `order=asc`，按发布时间正序展示系列文章（01 → 13），和阅读顺序一致。

**这里有一个已知缺口**：Repository 的方法没有接收 `context.Context`，查询用的是 `r.db` 而不是 `r.db.WithContext(ctx)`。后果是客户端断开连接后，已经在跑的 SQL 不会被取消，慢查询会继续占着连接。正确做法是每个 Repository 方法都收 `ctx` 并传给 GORM，这是下一步要补的（第 13 篇也列了）。

## 第 5 层：响应与错误

所有接口返回同一个外壳：

```json
{ "code": 0, "message": "ok", "data": { "list": [], "total": 0, "page": 1 } }
```

`code` 为 0 表示成功，非 0 是业务错误。为什么不用 HTTP 状态码区分一切？因为业务错误太多了——"用户名已存在"、"评论太频繁"、"文章不存在"，如果每个都对应一个 HTTP 状态码，前端要维护一张巨大的映射表。所以约定：**HTTP 状态码表达传输层结果，code 表达业务结果**。

错误翻译集中在 `handler/errors.go`：

```go
func fail(c *gin.Context, err error, fallback string) {
    switch {
    case errors.Is(err, service.ErrNotFound):
        response.NotFound(c, err.Error())        // 404
    case errors.Is(err, service.ErrUnauthorized):
        response.Unauthorized(c, err.Error())    // 401
    case errors.Is(err, service.ErrConflict):
        response.Conflict(c, err.Error())        // 409
    case errors.Is(err, service.ErrTooManyReqs):
        response.TooManyRequests(c, err.Error()) // 429
    case errors.Is(err, service.ErrInvalidInput):
        response.InvalidParam(c, err.Error())    // 400
    default:
        log.Printf("[ERROR] %s: %v", fallback, err)
        response.ServerError(c, fallback)        // 500 只回笼统信息
    }
}
```

这样 Service 只需要返回 `ErrNotFound` 这种语义化错误，不用知道该回 404 还是 400。

## 一条真实的坑：页码越界

最初的分页有个 bug：用户在第 3 页，然后切了分类，列表只剩 1 页，但 `page` 还是 3，于是查出来是空数组，页面显示"没有文章"。

修复放在 Service：查完之后如果 `total > 0` 且当前页超出总页数，就把 page 夹回最后一页。

```go
maxPage := (total + q.PageSize - 1) / q.PageSize
if maxPage > 0 && q.Page > maxPage {
    q.Page = maxPage
    return s.List(ctx, q)   // 重新查一次
}
```

这是个很小的细节，但它是"分层之后好处"的典型例子：这个修正只动了 Service，Handler 和 Repository 一行没改。

## 这条路径的代价

一次列表查询，代码跨了四个文件。如果只是做个 demo，这明显过度设计。

但这个博客不是 demo。我在它上面反复改需求：加标签筛选、加归档、加置顶、加状态。**分层真正省下的不是"写代码的时间"，而是"改代码时不用重新理解全局的时间"**。
