评论是全站唯一「不用登录就能写」的地方。

这句话的另一面是：它是全站唯一能被匿名脚本批量写入的地方。所以评论功能从来不是「存一条、读出来」这么简单，它同时要解决四个问题：

1. 数据怎么存，才能既支持回复、又不至于把查询写成 N+1
2. 匿名内容怎么保证不直接出现在页面上（审核）
3. 怎么拦住在几秒内灌几百条的脚本（限流）
4. 被 Nginx 反代之后，怎么知道请求到底来自谁（真实 IP）

这篇按这四个问题讲。代码在 `service/comment_service.go`、`repository/comment_repo.go` 和 `pkg/ratelimit/`。

## 两级评论：一维表 + parent_id

评论树最直觉的做法是「每条评论存一个 children 数组」，但关系型数据库里不会这么存。实际用的是一张扁平表加自关联：

```sql
CREATE TABLE comments (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  article_id BIGINT UNSIGNED NOT NULL,
  parent_id  BIGINT UNSIGNED NOT NULL DEFAULT 0,  -- 0 表示一级评论
  nickname   VARCHAR(50)  NOT NULL,
  content    VARCHAR(1000) NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,           -- 0 待审 / 1 通过
  ip         VARCHAR(45) NOT NULL DEFAULT ''
);
```

`parent_id` 理论上可以无限嵌套。我只做了**两级**：评论和回复。`parent_id = 0` 是一级，`parent_id > 0` 是回复；回复不能再被回复，Service 里直接拒掉。

为什么不做无限嵌套？不是实现不了，是**UI 上没法看**。手机上每层缩进 24px，三层之后正文只剩一半宽度；大多数博客主题最后都会在视觉上把深层回复压平。既然最终要压平，不如在数据层就限制住，查询和组装都简单一个数量级。

## 组装树：一次查询，内存分桶

如果按「先查一级评论，再对每条查它的回复」写，就是典型的 N+1：1 次主查询 + N 次子查询。评论一多，页面就慢在数据库往返上。

这个项目的做法是**一次查全，内存里组装**：

```go
// service/comment_service.go
all, _ := s.comments.ListByArticle(articleID, CommentApproved)

childMap := make(map[uint64][]model.Comment)
for _, c := range all {
    if c.ParentID > 0 {
        childMap[c.ParentID] = append(childMap[c.ParentID], c)
    }
}

nodes := make([]CommentNode, 0)
for _, c := range all {
    if c.ParentID != 0 {
        continue
    }
    nodes = append(nodes, CommentNode{Comment: c, Replies: childMap[c.ID]})
}
```

![一条 SQL 取回全部评论，按 parent_id 分桶再挂到父节点，查询次数恒定为 1](/diagrams/comment-tree.svg)

这里能这么写的前提，正是「只有两级」：分桶只需要一层 map，不需要递归。如果允许多层，就得反复遍历直到没有新的子节点，复杂度立刻上升。

代价是**一次把整篇文章的评论读进内存**。一篇文章几百条评论完全没问题；如果哪天单篇上万条，就得分页加载回复，那是另一个设计。

## 审核：默认不可见

新评论的 `status` 固定写 0：

```go
c := &model.Comment{
    ArticleID: articleID,
    ParentID:  in.ParentID,
    Status:    CommentPending,   // 0
    IP:        in.IP,
}
```

前台查询只带 `status = 1`，所以提交成功后页面不会立刻出现这条评论，提示是「等待审核后展示」。后台按 `status = 0` 拉待审列表，管理员点通过才改成 1。

这个状态机只有两个状态、两条边：

```
发表 ──► 待审核(0) ──通过──► 已展示(1)
             ▲                  │
             └──────打回─────────┘
```

删除则必须**连带删除回复**，而且要在事务里：

```go
func (r *CommentRepository) DeleteWithReplies(id uint64) error {
    return r.db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Where("parent_id = ?", id).Delete(&model.Comment{}).Error; err != nil {
            return err
        }
        return tx.Delete(&model.Comment{}, id).Error
    })
}
```

只删父评论会留下 `parent_id` 指向不存在记录的孤儿回复。前台组装树时这些回复既不会出现在顶层（`parent_id != 0` 被跳过），也挂不到任何父节点上，等于凭空消失，但数据库里还占着。

## 校验：长度按「字」算，不按字节

评论的输入校验里有两个容易写错的点。

第一，**长度用 `rune` 而不是 `len`**。`len("你好")` 在 Go 里是 6（UTF-8 字节数），不是 2。昵称限 50、内容限 1000，指的是字符数：

```go
if len([]rune(in.Nickname)) > maxNicknameLen { ... }
if len([]rune(in.Content)) > maxContentLen { ... }
```

第二，**回复的合法性要查库确认**，不能只信前端传的 `parent_id`：

- 父评论必须存在
- 父评论必须属于同一篇文章（否则能把回复挂到别的文章下）
- 父评论本身必须是一级（禁止回复的回复）
- 父评论必须已通过审核（不能回复一条访客看不到的评论）

这四条任何一条漏掉，都会出现「数据结构上合法、业务上荒唐」的记录。

## 限流：固定窗口会在边界放行双倍流量

评论接口公开可写，必须限流。项目默认同一 IP **60 秒内最多 3 条**。

最直观的实现是固定窗口：每分钟一个计数器，到点清零。它有一个致命缺陷——**窗口边界会放行双倍突发**：

```
00:59 打满 3 条
01:00 计数器清零，又打满 3 条
→ 实际 2 秒内进来 6 条
```

滑动窗口改成记录每次命中的时间点，每次判断只看「最近 60 秒内还有几条」：

```go
cutoff := now.Add(-l.window)
kept := list[:0]
for _, t := range list {
    if t.After(cutoff) {
        kept = append(kept, t)
    }
}
if len(kept) >= l.limit {
    retryAfter := kept[0].Add(l.window).Sub(now)
    return false, retryAfter
}
```

![固定窗口在整点边界会放行双倍请求，滑动窗口只统计最近 60 秒，没有可利用的边界](/diagrams/rate-limit-window.svg)

被拒绝时返回 `429`，并把「还要等几秒」一起返回。前端可以直接提示「请 42 秒后再试」，不用自己猜。

限流判断放在**参数校验最前面**。理由很直接：刷接口的脚本连参数都不该被处理，越早挡住越省资源。

还有一个内存细节：`hits` 这个 map 如果不清理，会被大量不同 IP 撑爆。所以每次调用顺手清理当前 key，另外每分钟做一次全量 GC，删掉所有已经过期的空 key。

## 真实 IP：`c.ClientIP()` 不是「读 socket」

限流按 IP 做，那 IP 从哪来？

```go
IP: c.ClientIP(),
```

看起来是取客户端地址，但 `ClientIP()` 内部会看 `X-Forwarded-For` / `X-Real-IP` 这些头。而**这些头是可以伪造的**，所以 Gin 需要一个「可信代理」名单：只有请求确实来自名单内的代理，才采信它带来的头。

生产环境前面是 Nginx，链路变成：

```
访客 → Nginx（127.0.0.1:80）→ Go（127.0.0.1:8090）
```

Nginx 把真实地址写进头：

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

后端必须配套：

```dotenv
TRUSTED_PROXIES=127.0.0.1
```

不配会怎样？Go 不采信 Nginx 带来的头，所有请求的「对端地址」都是 127.0.0.1。于是**全站所有访客被当成同一个 IP**——限流器把第 4 个评论者拦下来，理由是「你发得太频繁」，而其实他一条都没发过。

反过来，如果把 `TRUSTED_PROXIES` 配成 `0.0.0.0/0`（信任所有人），攻击者随便伪造一个 `X-Forwarded-For` 就能绕过限流。这个配置只有两种正确值：**填真实的代理地址，或者留空不信任任何头**。

## 这笔债

评论系统目前能挡住脚本，但挡不住「人工刷」：没有验证码、没有 Akismet 之类的垃圾内容识别、没有敏感词过滤。审核是目前唯一的兜底，量大了会变成体力活。

限流状态在进程内存里，也有三个明确的限制：

- 进程重启，计数清零
- 多实例部署时各算各的，实际额度会翻倍
- 内存占用随 IP 数量增长

这三个问题的统一解法是 Redis（`INCR` + `EXPIRE`），但那是引入一个新依赖的决策，不是「顺手加一下」。当前单机、低流量，先接受。
