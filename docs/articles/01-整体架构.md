这个博客一开始就不打算用现成的博客系统。

不是嫌 WordPress 重，而是我想搞清楚一件事：**从浏览器敲下回车，到屏幕上出现一篇文章，中间到底发生了什么**。不自己写一遍，这个问题永远只能背答案。

所以这套代码是边学边写的：后端从零用 Go 搭，前端用 Vue3 搭。它有 34 个接口、24 个单测、6 张表，跑在一台 1.6G 内存的云服务器上。

这篇文章讲整体架构——不是讲"我用了什么技术"，而是讲**每个位置为什么是它，以及我砍掉了哪些东西**。

## 一条请求的完整路径

![整体架构](/diagrams/architecture.svg)

拆开看只有三个角色：

| 位置 | 它负责 | 它不负责 |
|---|---|---|
| Nginx | 发静态文件、反代 `/api` 和 `/uploads`、终结 HTTPS | 不碰任何业务逻辑 |
| Go 服务 | 所有 `/api/v1/*` 接口、鉴权、限流、图片落盘 | 不发静态文件 |
| MySQL | 存 6 张业务表 | 不做缓存（没有 Redis） |

最关键的一条分工是：**静态文件绝不经过 Go**。

原因很直接。Go 的 `net/http` 发一个文件要经过路由匹配、中间件链、`http.ServeFile`，而 Nginx 用 `sendfile(2)` 直接在内核层把文件描述符拷到 socket。同样一个 140KB 的 JS 文件，Nginx 的吞吐能高出好几倍，而且不占 Go 的 goroutine。

所以 Nginx 的配置里静态文件是这么发的：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}

location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

`try_files` 那行是 SPA 的命门。前端用 history 模式，`/article/1` 在磁盘上没有对应文件，必须回退到 `index.html` 让 Vue Router 接管；不退的话，用户刷新详情页就是 404。

而 `/assets/` 下的文件名带内容 hash，可以放心让浏览器缓存一年——只要文件内容变了，hash 就变，URL 也就变了。

## 为什么是这三个，不是别的

**Go 而不是 Node / Python**：我要练的是后端。Go 的 `net/http` 和 `context` 逼着你面对并发和超时这些概念，而且编译出来是单个静态二进制，22MB，扔到服务器上就能跑，不用装运行时。这一点在第 10 篇讲部署时会体现得很明显。

**Gin 而不是标准库裸写**：标准库够写，但路由分组、参数绑定、中间件链要自己造一遍。Gin 在这三件事上的抽象刚好够用，又没有 Spring 那种重量。这一篇不展开，第 03 篇讲分层时会说到它的代价。

**GORM 而不是 `database/sql` + 手写 SQL**：这是我最犹豫的一个决定。GORM 的 `AutoMigrate`、关联预加载写起来确实快，但它的"魔法"也掩盖了真实的 SQL。所以项目里定了一条规矩：**迁移脚本不用 AutoMigrate，全部手写 SQL 文件**。原因在第 04 篇讲数据建模时写过。

**MySQL 而不是 PostgreSQL**：没有技术原因，是国内后端岗位用得最多，练它面试能对上。

**Vue3 而不是 React**：也谈不上偏好。组合式 API 的 `script setup` 写起来比 Options API 干净，而且这个博客的交互复杂度用不上 React 那套生态。

## 被砍掉的东西

这部分比"用了什么"更能说明架构。

**没做微服务。** 一台机器、一个 Go 进程、一个数据库。分服务的好处是独立扩缩容和故障隔离，但这个博客的峰值可能就是几个人同时看——分成五个服务只会让我多写五份配置、多调五个健康检查。

**没上 Redis。** 限流用的是进程内内存（第 06 篇会讲它的缺陷），分类和标签每次查库。在数据量是两位数的时候，加一层缓存除了增加"缓存和数据库不一致"的 bug，没有任何收益。

**没做对象存储。** 图片直接落在 `/opt/blog/backend/uploads/`，由 Nginx 反代出去。代价是备份要连目录一起备，优点是少一个外部依赖、少一套密钥管理。

**没做全文搜索。** 搜索就是 `LIKE '%关键词%'`，索引完全用不上。数据量上到十万级就会慢，但我知道它慢在哪、也知道该怎么换（第 04 篇会讲）。

这些"不做"不是能力不够，是**在当前规模下它们带来的复杂度超过了收益**。架构的难点从来不是加东西，是克制住不加。

## 代码长什么样

后端按职责分了七层，每一层只依赖下一层：

```
backend/
├── cmd/server/          程序入口：读配置 → 连库 → 装路由 → 优雅关闭
└── internal/
    ├── config/          读 .env，校验必填项
    ├── database/        GORM 连接与连接池
    ├── model/           6 个实体
    ├── repository/      数据访问（只有这层写 SQL）
    ├── service/         业务规则（校验、事务、状态流转）
    ├── handler/         HTTP 层（参数、响应、错误翻译）
    ├── middleware/      RequestID / 日志 / Recover / CORS / JWT
    ├── router/          路由与依赖装配
    └── pkg/             response / jwt / hash / pagination / authctx
```

这个分层在第 03 篇会详细拆，这里只需要记住一条规则：**Handler 不碰 SQL，Repository 不碰 HTTP**。

分层的代价是写一个接口要改四个文件。好处是当我想加"文章草稿定时发布"这种功能时，只需要动 service 和 repository，HTTP 层一行都不用改。

## 一些数字

| 项 | 数量 |
|---|---|
| 后端接口 | 34 个（公开 8、认证 4、后台 15、诊断 4，其余为静态资源） |
| 数据库表 | 6 张（users / categories / tags / articles / article_tags / comments） |
| 后端单测 | 24 个 |
| 前端页面 | 前台 6 页 + 后台 5 页 |
| 后端二进制 | 22 MB（`CGO_ENABLED=0` 静态链接） |
| 前端产物 | dist 约 1.7 MB（JS/CSS 约 1.0 MB，最大包 141 KB） |
| 服务器配置 | 1 vCPU / 1.6 GB 内存 / 20 GB 磁盘 |
