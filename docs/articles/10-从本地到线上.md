本地跑通只要两条命令：一个终端 `make run`，另一个 `pnpm dev`。到公网能打开，中间隔着六个必须做对的动作。

交叉编译出一个 Linux 能跑的文件；把静态文件和动态接口分开走；用 systemd 把进程托管起来；替换二进制时用 `mv` 而不是覆盖；上线后逐条验收；出错时按层排查。

前五个是操作，第六个是纪律。那天从 15:36 折腾到 17:40，两个多小时，真正卡住我的不是部署，是域名状态——而我在那之前已经重启了两次服务。

顺手记一个本地的小坑，它和线上无关但同样值得记：`vite.config.js` 里 `server.host` 必须显式写 `127.0.0.1`。默认值是 `localhost`，macOS 上 Node 会优先解析成 `::1`，于是 Vite 只监听 IPv6，浏览器输 `127.0.0.1:5173` 打不开。开发期的代理也刻意和线上同形：`/api` 和 `/uploads` 都转给 8090，这样前端代码在本地和线上走的是同一套相对路径，不必为环境写分支。

## 四个角色，三次进程跳转

![浏览器经 Nginx 到 Go 服务再到 MySQL，三个 location 决定谁发静态文件](/diagrams/deploy-topology.svg)

请求从浏览器出发，先到 Nginx（对外 80/443），反代到只监听 `127.0.0.1:8090` 的 Go 进程，Go 再连本机 MySQL。中间换了两次进程、一次协议。

最要命的一条分工是：**静态文件绝不经过 Go**。

Go 发一个文件要经过路由匹配、中间件链、`http.ServeFile`，文件内容先读进用户态缓冲再写进 socket，而且这条请求会占住一个 goroutine 直到发完。Nginx 用的是 `sendfile(2)`——内核把文件页缓存直接递到 socket，不经过用户态。

我不打算编一个"Nginx 快 3 倍"的数字，因为没测过。但量级对比是清楚的：前端 `dist/` 约 1.7MB、96 个文件（实测：JS/CSS 约 1.0MB，讲解图 148KB，截图 280KB），打开首页会发十几个静态请求；而后端总共 34 个接口。把静态请求赶去挤 goroutine 和中间件链，等于拿最贵的资源干最便宜的活。

Nginx 里三条 `location` 把这件事写死了：

```nginx
location / {
    try_files $uri $uri/ /index.html;   # 静态文件 + SPA 回退，Nginx 自己发
}
location /assets/  { expires 1y; add_header Cache-Control "public, immutable"; }
location /api/     { proxy_pass http://127.0.0.1:8090; }
location /uploads/ { proxy_pass http://127.0.0.1:8090; }
```

`proxy_pass` 后面**不能带结尾斜杠**。带了，Nginx 会把匹配到的 `/api/` 前缀替换掉，后端收到的是 `/v1/articles`，直接 404。这个坑很小，但排查起来会怀疑到路由表上去。

备案期间这套配置监听 8080。国内服务器的 80 端口对未备案域名会被拦，所以先用 `IP:8080` 验证整条链路；备案通过后把 `listen` 改回 80，再用 certbot 加 443。

## 构建：产物只有一个文件

`deploy/build.sh` 做三件事：`go vet ./...` 过一遍静态检查，交叉编译后端，然后 `pnpm install --frozen-lockfile && pnpm build`。

后端那行是关键：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags "-s -w" -o bin/blog-server ./cmd/server
```

第一次我只跑了 `make build`，在 Mac 上产出的自然是 `darwin/arm64`，传到服务器上执行，报 `cannot execute binary file`。`GOOS=linux GOARCH=amd64` 解决"能不能跑"，`CGO_ENABLED=0` 解决"跑起来会不会缺东西"——关掉 cgo 之后是纯静态链接，不依赖服务器的 glibc 版本，不会出现 `GLIBC_2.xx not found`。

验证不看输出日志，看文件本身：

```bash
file backend/bin/blog-server
# ELF 64-bit LSB executable, x86-64, statically linked
du -sh backend/bin/blog-server frontend/dist
# 22M  和  1.0M
```

22MB 单文件扔上去就能跑，服务器上不需要装 Go，也不需要 Node。这一点在这台机器上不是优化，是前提：1 vCPU / 1.6GB 内存 / 20GB 磁盘（剩 11GB），在上面装 toolchain、装 node_modules 再编译，是给自己找事。

前端那半边的体积也调过一轮。最初 `app.use(ElementPlus)` 全量引入，dist 是 1.7MB，最大单个 JS 830KB、CSS 362KB。改成 `unplugin-auto-import` 加 `unplugin-vue-components` 按需引入、语言包用 `<el-config-provider>` 下发之后，dist 降到 1.0MB，最大 JS 141KB、CSS 25KB（都是实测值）。在这么小的机器上，这不是"快一点"的问题——每个多出来的字节都要靠那点内存和带宽去扛，而它省下来的是一次白屏等待。

还有一个和网络有关的坑。`go.mod` 要求 Go 1.26.4，本机是 1.24.5，首次构建会下载 toolchain，然后去 `sum.golang.google.cn` 做校验——这个地址会连接超时。只设 `GOPROXY` 没用；设 `GOSUMDB=off` 会直接报 `checksum database disabled by GOSUMDB=off`。正确做法是让代理代答校验：

```bash
export GOPROXY=https://goproxy.cn,direct
export GOSUMDB=sum.golang.org
```

这两行现在写进 `build.sh` 当默认值（`${GOPROXY:-...}` 的写法，外部设了就以外部为准）。

## Nginx 四行，systemd 四个字段

站点配置里有四处是真会出事的：

```nginx
client_max_body_size 8m;                 # 必须 ≥ 后端 UPLOAD_MAX_MB（默认 5MB）

location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}

location /api/ {
    proxy_pass http://127.0.0.1:8090;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

`try_files $uri $uri/ /index.html` 是 SPA 的命门：前端用 history 模式，`/article/1` 在磁盘上没有对应文件，必须回退到 `index.html` 让 Vue Router 接管，否则用户刷新详情页就是 404。

`/assets/` 可以 `expires 1y` 加 `immutable`，因为文件名带内容 hash，内容一改 URL 就变。但 `index.html` 绝对不能缓存——发版时 `rsync --delete` 会删掉旧的 assets，如果用户手里还是旧 index.html，页面会去请求一批已经不存在的文件，白屏。

另外几项不进"四行"，但漏了会后悔：`gzip on` 加 `gzip_min_length 1024`，压缩类型里补上 `application/javascript`、`image/svg+xml`——静态文件不经过 Go，压缩只能在这里补；三个安全头 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: strict-origin-when-cross-origin`；`proxy_connect_timeout 5s` / `proxy_read_timeout 30s`，后者和 Go 的 `WriteTimeout` 30s 对齐——如果 Nginx 先断开，Go 还会继续写完一个没人接收的响应，白白占着 goroutine。

`X-Real-IP` 和 `X-Forwarded-For` 只是"声称"，后端信不信由自己决定。所以还要在 `.env.prod` 里配 `TRUSTED_PROXIES=127.0.0.1`。这两件事必须成对出现：漏了后半句，评论表里所有 `ip` 都是 `127.0.0.1`，而评论限流是按 IP 计的（默认 3 条 / 60 秒），第 4 个人发评论就会拿到 429——全站用户被当成同一个人。

`client_max_body_size 8m` 要大于等于后端的 `UPLOAD_MAX_MB`（默认 5MB）。小于的话，上传请求在 Nginx 就被 413 拒掉，Go 那边一行日志都不会有。这类"应用日志干净、请求根本没到"的问题最难查，因为所有能看的证据都指向"没问题"。

托管用 systemd：

```ini
[Service]
User=blog
Group=blog
WorkingDirectory=/opt/blog/backend
Environment=ENV_FILE=/opt/blog/backend/.env.prod
ExecStart=/opt/blog/backend/bin/blog-server
Restart=always
RestartSec=5s
KillSignal=SIGTERM
TimeoutStopSec=15s
ProtectSystem=strict
ReadWritePaths=/opt/blog/backend/uploads
StandardOutput=journal
```

`User=blog` 不是形式主义：用 root 跑一个对外开放 HTTP 端口的程序，等于把这个入口的每一个漏洞都放大成整台机器的漏洞。

`TimeoutStopSec=15s` 这个数字要和代码对齐。`main.go` 里优雅关闭给的是 10 秒（`context.WithTimeout(..., 10*time.Second)`），systemd 这里留 15 秒余量——排空期间发 SIGTERM 之后，超过 15 秒才 SIGKILL。如果反过来配成 10 秒或更短，程序正写到一半的响应会被直接切断。这种配置平时看不出问题，压测或者恰好有慢请求时才炸。

`ProtectSystem=strict` 把整个文件系统设成只读，所以上传目录必须显式写进 `ReadWritePaths`，否则上传接口会 500——而报错信息只会说"写入失败"，不会告诉你"是沙箱不让写"。

`ENV_FILE` 指向 `.env.prod`。程序对这个变量的处理是：设了却找不到文件就直接报错退出，不静默降级。理由很实际——静默降级会让你以为走了生产配置，其实用的是默认值，而默认值里的 `APP_ENV=dev` 会把 `/debug/*` 路由开到公网。

日志不自己写文件、不做轮转，全部交给 journald，用 `journalctl -u blog-server -f` 看。

上线前还有六项要逐条确认，它们和"能不能跑"无关，只和"跑起来安不安全"有关：

- `.env` / `.env.prod` 不进 Git。这一步我差点翻车：`.gitignore` 最初只有 `backend/.env` 一条，生成 `.env.prod` 后 `git check-ignore` 提示未被忽略——数据库密码和 JWT 密钥会直接进仓库。改成 `backend/.env.*` 加 `!backend/.env.example`。
- `JWT_SECRET` 换成 `openssl rand -hex 32` 的新值。本地那份文件在聊天工具里传过，按泄露处理。
- `APP_ENV=prod`。验收命令是 `curl /api/v1/debug/db` 返回 404，未登录取 `/api/v1/admin/articles` 返回 401。
- HTTPS 交给 certbot，`certbot renew --dry-run` 验续期。备案没下来之前签不出来，因为 80 端口验证走不通——这是备案的第二个硬约束。
- MySQL 只允许本机连：账号是 `'blog'@'localhost'`，连接串写 `127.0.0.1`，3306 不进安全组。
- `.env.prod` 权限 600、属主 `blog`。

## 发布：传 .new，mv，然后 curl 一次

![五步发布流水线：构建、上传 .new、原子替换、重启与健康检查，失败回滚](/diagrams/release-pipeline.svg)

直接 `rsync` 覆盖正在运行的那个二进制，会遇到两个问题。轻的是内核拒绝写入正在执行的文件（`Text file busy`）；重的是 rsync 中途失败，留下一个半截的文件，下次 `systemctl restart` 时它既跑不起来，也不是原来那一版。

`mv` 不一样。同一个文件系统内的 `mv` 是 `rename(2)`，原子操作——目标路径上要么是完整旧文件，要么是完整新文件，没有中间状态。

所以流程是五步：

```bash
# 1. 本机构建
./deploy/build.sh

# 2. 传成 .new，不碰正式文件
rsync -az backend/bin/blog-server blog@server:/opt/blog/backend/bin/blog-server.new

# 3. 原子替换 + 重启
ssh blog@server 'mv /opt/blog/backend/bin/blog-server.new \
  /opt/blog/backend/bin/blog-server && sudo systemctl restart blog-server'

# 4. 验活
curl -s http://127.0.0.1:8090/api/v1/ping

# 5. 看日志
journalctl -u blog-server -n 50 --no-pager
```

升级前的备份是两条命令，一条管数据，一条管文件：

```bash
mysqldump -ublog -p blog | gzip > /backup/blog-$(date +%F).sql.gz
tar czf /backup/uploads-$(date +%F).tar.gz /opt/blog/backend/uploads
```

回滚就是把 `.bak` 拷回来再重启一次。第一次升级我忘了留 `.bak`，真要回滚时只能重新构建一版——性质完全不同：前者是"恢复到已知状态"，后者是"再发一次版，希望这次对"。

这套流程有一个诚实的缺口：**它不是零停机**。`systemctl restart` 之后进程要重新监听 8090，那一下新请求会拿到 502；优雅关闭保证的是"已经进来的请求"写完，管不了"还没进来的请求"。要真做平滑，得让 Nginx `upstream` 挂两个端口、轮流切换，这套单进程部署没做——按这个博客的访问量，秒级空窗的代价小于维护两套端口的复杂度。

前端同样是 `rsync -az --delete frontend/dist/ → /var/www/blog/dist/`。`--delete` 保证服务器上不留旧 hash 文件，代价是它必须和 `index.html` 的 no-cache 配套：缺了 no-cache，就会出现"用户手里是旧页面、服务器上已经删掉了旧文件"。

迁移脚本只加不改这条规矩，在这里开始还债：回滚代码通常不需要回滚表结构，因为新代码总是兼容旧结构。这是当初定"迁移文件永久冻结"的回报。

## 那天域名是 clientHold，不是我的配置错

前五步做完，服务器内部全通了：`curl 127.0.0.1:8090/api/v1/ping` 有响应，`curl 127.0.0.1:8080/` 返回 200。但外面打不开。

我先怀疑了自己的配置，重启了两次服务。这是错的。

正确的顺序是按层走，每层用各自的证据，不用上一层的结论推断下一层。

**第一层，域名解析。** 权威解析器直接问，绕开本地缓存：

```bash
curl -s "https://dns.alidns.com/resolve?name=youzhichong.xyz&type=A"
# Status=3 就是 NXDOMAIN，域名根本不存在
```

结果是没有 A 记录。到这里还不能下结论——可能是记录没加，也可能是加了解析不生效。

**第二层，注册局状态。** 这一步是我当天最大的收获。查 RDAP：

```bash
curl -s "https://rdap.centralnic.com/xyz/domain/youzhichong.xyz"
```

`status` 里出现了 `client hold`，而 `last changed` 停在 `2026-07-01T08:21:29Z`——五个月没动过。

`clientHold` 的意思是注册商把域名挂起了，注册局因此不发布 NS 委派。递归解析器在 `.xyz` 那一层就拿到 NXDOMAIN，根本走不到阿里云的解析服务器。所以在这个状态下，改任何解析记录、加任何 A 记录、等多久缓存过期，都不会生效。

而阿里云控制台显示"实名认证成功"，只是说阿里云审完了身份证，不代表注册局侧已经解除。**控制台的状态和应用能否访问之间，隔着一整个注册局。**

完成实名认证后，注册局在 17:10 解除了 hold（`last changed` 更新为当天），17:39 全球解析生效，中间约 29 分钟——那是递归解析器上旧 NXDOMAIN 的负缓存到期时间。

**第三层，端口和安全组。** 那天还有一个现象：服务器内 `curl 127.0.0.1:8080` 正常，外网 `nc -z IP 8080` 不通。这组对照证据直接指向网络层而不是应用层，处理方式是在安全组放行 8080（端口范围要写 `8080/8080`，只写 `8080` 会报错）。放行之后外网立刻通。

**第四层，证书。** 只有前三层都通了，`certbot` 的 80 端口验证才有意义。

**第五层才是应用。** 应用层的问题看 `journalctl`，它一定会有输出——如果一个请求连日志都没留下，那问题在它之前。

这套顺序的价值不在于快，在于不会把一个问题变成两个：在配置没错的时候重启服务，等于给自己制造了一次"日志被冲掉、状态被重置"的额外变量。重启是最便宜的动作，也是最容易掩盖问题的动作。

---

最后说这套部署还没做到什么，写清楚比假装完整好。

没有 CI/CD。`build.sh` 靠手动跑，`go vet`、24 个单测、前端构建，全凭我记得。没有容器化，换一台机器要重跑 `server-init.sh`，而那个脚本自己的注释里还写着"没有在真实服务器上跑过"。没有监控和告警，服务挂了只能靠我发现——现在唯一的"监控"是我偶尔 `curl` 一下。单机没有高可用，Nginx、Go、MySQL 挤在同一台 1 vCPU 的机器上，重启任何一次都是全站短暂不可用。备份也是手动的两条命令，没有定时任务，更没有演练过恢复。

这些都不是不知道怎么做，是当前规模下它们的复杂度超过了收益。但"知道欠着什么"和"不知道自己欠着"是两回事：前者是排期问题，后者是事故。
