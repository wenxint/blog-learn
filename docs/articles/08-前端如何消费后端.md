前端代码一多，最先烂掉的地方不是某个页面写错了，是**每个页面各自写 axios、各自拼错误提示**。

第一版首页里是这样的：

```js
const res = await axios.get('http://127.0.0.1:8090/api/v1/articles')
if (res.data.code === 0) {
  articles.value = res.data.data.list
}
```

然后详情页抄一遍，归档页抄一遍，只把地址和字段名改掉。当时觉得没什么：能跑就行。

问题在第二周出现。后端把统一响应加上 `message` 字段，我在三个文件里翻 `res.data.data`；改端口那天，全项目搜 `127.0.0.1:8090` 替换；再后来要加"token 过期自动踢出"，我发现得在十几个调用点各加一段判断。

**重复不会一次性把代码搞崩，它让每一次改动都变贵。** 所以前端的第一个正式动作不是写页面，是把重复的部分收成两个文件：`router/index.js` 和 `api/request.js`。

这套前端现在是 23 个源文件、约 4100 行（含注释）；`dist/` 构建产物 96 个文件、约 1.7 MB，其中 JS/CSS 约 1.0 MB，讲解图与截图约 0.4 MB（as-built 实测）。

## 路由：布局是父路由，页面只写内容

路由表最关键的一个决定：**用布局当父路由，页面当子路由**。

```js
{
  path: '/',
  component: () => import('../layouts/DefaultLayout.vue'),
  children: [
    { path: '', name: 'home', component: () => import('../views/Home.vue'), meta: { title: '首页' } },
    { path: 'article/:id', name: 'article-detail', component: () => import('../views/ArticleDetail.vue'), meta: { title: '文章详情' } },
    // archive / tags / about 同理
  ],
}
```

`DefaultLayout.vue` 里只有一个站点头部、一个 `<RouterView />`、一个页脚。所以五个前台页面里都没有 `<header>`，也没有哪一处会忘记写页脚——**它们根本不需要知道壳子的存在**。

![布局做父路由后，前台和后台的页面各自继承自己的壳子，不必重写](/diagrams/route-tree.svg)

后台是同一套结构，套的是 `AdminLayout.vue`（左侧菜单 + 顶栏），而 `meta: { requiresAuth: true }` 只写在 `/admin` 这一层。

登录页是故意不套布局的：它单独挂在 `/admin/login`，不放进 `AdminLayout` 的 children。理由很实际——没登录的人不该先看见侧边栏再被弹回登录页。404 路由放在数组最后，`path: '/:pathMatch(.*)*'` 兜底。

第二件事是懒加载。每个页面都是 `() => import(...)`，构建后每个页面一个独立 chunk。本地的 `dist/assets` 能直接对上：

| 文件 | 大小 | 什么时候下载 |
|---|---|---|
| `Home-CJd9YO39.js` | 5,630 字节 | 进首页 |
| `ArticleDetail-BFUfgSqb.js` | 4,692 字节 | 进详情页 |
| `ArticleEdit-C-Nh9UnE.js` | 27,891 字节 | 进后台编辑器 |
| `markdown-DtHCqlQH.js` | 144,279 字节 | 进详情页或编辑器 |

最后一行是我特意分开的：Markdown 渲染那套（marked + 高亮 + DOMPurify）占了 141 KB，首页一个字都不需要它。如果全都静态 import 进主包，每个访客打开首页都要先下这 141 KB 才能看见文章列表。

懒加载的代价是首屏多一次 chunk 请求。HTTP/2 下多一个请求的代价已经很小，省下的却是实打实的解析时间——这笔账我算得过来。

### history 模式和那行 try_files

Router 用的是 `createWebHistory()`，URL 长这样：`/article/1`，没有 `#`。好处是链接干净、刷新不丢、分享出去能直接打开；代价是**服务器必须配合**。

因为磁盘上并不存在 `article/1` 这个文件。请求打到 Nginx，它找不到对应文件，就回 404——Vue Router 连执行的机会都没有。

修法是一行：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

意思是：先按路径找文件，找不到就把 `index.html` 发回去。浏览器拿到 SPA 的壳，Router 读到 `location.pathname` 是 `/article/1`，才渲染详情页。

`deploy/nginx.conf` 里那行注释我写得很直白：必须回退到 `index.html`，否则刷新页面 404。这是 SPA 上线第一天最容易踩的坑，而且本地 `pnpm dev` 完全复现不了——Vite 开发服务器自己处理了回退。

同一个文件里还有一条容易忘的：`client_max_body_size 8m`。后端 `UPLOAD_MAX_MB` 是 5，Nginx 默认只收 1 MB，上传 2 MB 的封面会先被 Nginx 用 413 拒掉，Go 那边一条日志都不会有。

### 标题、滚动和登录守卫

三件小事，都挂在 Router 上：

```js
router.afterEach((to) => {
  document.title = to.meta.title ? `${to.meta.title} · 我的博客` : '我的博客'
})
```

`meta.title` 写在每条路由上，`afterEach` 统一改 `document.title`。这样浏览器标签页、历史记录、收藏夹里是"文章详情 · 我的博客"，而不是一串路径。

`scrollBehavior() { return { top: 0 } }` 让每次跳转回到顶部。没有它，从首页底部点进文章会停在半截。

登录守卫是唯一有分支的：

```js
router.beforeEach((to) => {
  if (!to.meta.requiresAuth) return true
  const token = localStorage.getItem('token')
  if (token) return true
  return { name: 'admin-login', query: { redirect: to.fullPath } }
})
```

`to.meta` 是父路由到子路由**合并后**的对象。`requiresAuth` 只写在 `/admin` 上，但 `/admin/articles`、`/admin/comments` 全都继承了它——这就是"整组挂"而不是"逐条挂"的价值：以后加一个后台页面，不可能忘记加守卫。

`?redirect=` 是体验细节：从 `/admin/articles/new` 被踢去登录，登录成功后应该回到新建页，而不是文章列表。`Login.vue` 里就一句 `router.replace(route.query.redirect || '/admin/articles')`。

**但它只是体验。** 前端守卫改一下 localStorage 就能绕过——真正的拦截在后端每个接口验 token。这句话我在路由文件里也留成了注释。

## 请求层：只做四件事

`api/request.js` 一共 61 行，做四件事。

```js
const request = axios.create({
  baseURL: '/api/v1',
  timeout: 10000,
})
```

**一、请求前塞 token。** 请求拦截器从 localStorage 读 token，塞进 `Authorization: Bearer <token>`。`api/` 下面那些函数因此没一个需要记得带 token。

**二、剥掉响应外壳。** 后端永远返回 `{code, message, data}`，响应拦截器直接 `return body.data`。页面里拿到的就是业务数据本身，不用写 `res.data.data.list`。

**三、HTTP 200 但业务失败也算失败。**

```js
if (body && body.code !== 0) {
  ElMessage.error(body.message || '请求失败')
  return Promise.reject(new Error(body.message || '请求失败'))
}
return body.data
```

这行是整套封装的核心判断。后端约定"HTTP 状态码表达传输层结果，code 表达业务结果"，那前端就必须同时看两个维度：HTTP 200 只说明这次 HTTP 请求成功了，`code: 10005`（冲突）照样是失败。

**四、HTTP 层错误分三支。** 401 清掉 localStorage 里的 `token` 和 `user`，提示"登录已过期"；403 只提示"没有权限"，不动登录态；其他一律弹后端给的 `message`。

401 和 403 必须分开：401 是"我不知道你是谁"，该踢去登录；403 是"我知道你是谁，但你不能干这个"，把已登录的人踢出去是错的。

### 页面里为什么只剩成功分支

因为失败路径全被拦截器接住了。页面只需要管好 loading：

```js
loading.value = true
try {
  article.value = await fetchArticleDetail(route.params.id)
} catch {
  router.replace('/')   // 这里不弹提示，是因为拦截器已经弹了
} finally {
  loading.value = false
}
```

`ArticleEdit.vue` 的保存函数里，catch 块甚至只有一句注释：

```js
} catch {
  // 拦截器已提示
}
```

这不是偷懒，是**责任已经有人负了**。如果每个页面再弹一次，同一个错误会弹两层，用户得手动关两次弹窗。

有一个取舍要说清：401 时拦截器清的是 localStorage 的两把 key，不是 Pinia 里的 `token` ref。要清 store 就得在 `request.js` 里 import `stores/user.js`，而那个 store 又 import 了 `api/auth.js` → `api/request.js`，直接绕成循环依赖。所以现在的行为是：登录态在 localStorage 里立刻失效，Pinia 的 ref 要等页面刷新或下一次路由才对齐。用户看到的提示是对的，内部状态有一小段时间不同步——这是我知道、但选择留着的一处不一致。

## 跨域：用代理，而不是让后端开 CORS

开发期前端在 `127.0.0.1:5173`，后端在 `127.0.0.1:8090`。端口不同，浏览器就认为是跨域。

有两条路：后端加 CORS 头，或者前端做代理。我选代理。

```js
server: {
  port: 5173,
  proxy: {
    '/api': { target: 'http://127.0.0.1:8090', changeOrigin: true },
    '/uploads': { target: 'http://127.0.0.1:8090', changeOrigin: true },
  },
}
```

理由是**形态一致**：生产环境是 Nginx 把 `/api` 反代到 8090，本来就同源；开发期用代理以后，本地和生产走同一套路径规则，前端那行 `baseURL: '/api/v1'` 一行都不用改。

CORS 的麻烦在于它是一堆细节的组合：`OPTIONS` 预检、`Access-Control-Allow-Credentials`、自定义头要列进 `Allow-Headers`、带凭证时 `Allow-Origin` 不能是 `*`。任何一项没对齐，报错信息都很含糊。而代理让**根本没有跨域这回事**——浏览器看到的一直是同源，整体少一个可变量。

生产那边对应的是 `deploy/nginx.conf`：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8090;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

顺带埋了一个坑：反代之后 Go 拿到的 `RemoteAddr` 全是 127.0.0.1，评论限流会把全站用户当成同一个人。所以后端 `.env` 里必须配 `TRUSTED_PROXIES=127.0.0.1`，它才采信 `X-Forwarded-For`。

还有个开发期的真实故障：`vite.config.js` 里 `host` 显式写成 `'127.0.0.1'`。默认值是 `localhost`，macOS 上 Node 会优先解析成 `::1`，于是浏览器开 `127.0.0.1:5173` 直接连不上。这个坑不报错、不提示，就是转圈。

## 状态：Pinia 只存 token 和 user

`stores/user.js` 里只有两个状态：`token` 和 `user`，外加两个派生值 `isLoggedIn`、`isAdmin`。

**没有存文章列表。** 这是我后来才想明白的：

- 列表是服务端数据的一份副本。存了就要处理失效——新发文章、删了文章、别人加了评论，缓存怎么更新？最省事的做法是不缓存。
- 筛选条件放在 URL 里，刷新后能重建出同样的请求。既然 URL 能唯一确定一份列表，缓存就没有存在意义。
- 这个数据量下，一次列表查询的耗时远小于维护缓存一致性的成本。

登录态反而必须持久化，因为刷新页面不能把人踢出去。所以 token 落在 localStorage。

**这个选择的代价写在 store 的注释里**：localStorage 能被 JS 直接读，也就意味着能被 XSS 直接偷。换成 `httpOnly` Cookie 能挡住这种读取，但在"JWT 无状态 + 纯前后端分离"的形态下，Cookie 又要处理 CSRF。这个取舍后面还会再出现。

### 刷新后为什么要重新拉一次 profile

`AdminLayout` 挂载时会调 `userStore.loadProfile()`。

因为 localStorage 里那份 `user` 可能是旧快照：昨晚改了昵称，今天打开后台侧边栏还是旧名字；角色从 author 变成 admin 也不会自动生效。所以每次进后台都静默拉一次 `/auth/profile`，成功后覆盖 localStorage。

这个函数里有一个我改过的地方，也是这套前端唯一一次"数据丢失级"的 bug。

原来是这样：

```js
} catch {
  logout()
}
```

看起来合理——拉不到用户就登出。实际上它把**所有**失败都当成"凭证失效"：后端重启三十秒、地铁里断网、请求超时十秒，任何一次 profile 失败都会清掉登录态。那天我在改文章，后端重启了一次，页面直接跳登录页，没保存的内容全没了。

修复只认 401：

```js
} catch (err) {
  if (err?.response?.status === 401) {
    logout()
  }
}
```

关键在于那个 `?.`：超时和网络错误的 `error.response` 是 undefined，直接取 `status` 会抛 TypeError。**"网络失败"和"身份失效"是两件事**，混在一起处理，代价就是用户丢数据。

## 列表：把筛选条件放进 URL

首页有分类、标签、月份、关键词四种筛选，还有分页。这些状态全在地址栏里：

```
/?tag_id=2&tag_name=Vue&page=1
```

`Home.vue` 里两个函数：`syncFromQuery()` 进来时读 `route.query`，`syncToQuery()` 变化时写回去，用的是 `router.replace` 而不是 `push`——搜索框每敲一个字都 push 一条历史的话，浏览器返回键就废了。

好处有三个：链接能分享、刷新不丢筛选、归档页和标签页可以直接跳过来。

```js
// Archive.vue
router.push({ path: '/', query: { month } })
// Tags.vue
router.push({ path: '/', query: { tag_id: tag.id, tag_name: tag.name } })
```

`tag_name` 只为了在筛选条上显示标签名，它不参与请求——`#2` 没人看得懂。

### 切筛选必须回第 1 页

```js
function resetAndLoad() {
  page.value = 1
  loadArticles()
}
```

不这么做就会出现那个经典 bug：停在第 5 页，切了个只有 2 页的分类，列表空白，用户以为没文章。

后端也做了兜底：查到 `total` 之后如果当前页超过总页数，就把页码夹回最后一页。两边都做不是重复，是**前端保证不会发出这种请求，后端保证这种请求不会有坏结果**。

### loading / empty / error 三态

列表页的三种状态都是显式的：

```html
<ElSkeleton v-if="loading" :rows="5" animated />
<template v-else>
  <ElEmpty v-if="articles.length === 0" description="没有找到文章" :image-size="80" />
  <ul v-else class="post-list">…</ul>
</template>
```

empty 的文案还分了场景：首页无筛选时是"还没有发布文章"，有筛选时是"没有找到文章"。同一个空列表，两种意思。

页面最终长这样：

![桌面端首页：13 篇文章、分类筛选与搜索都来自同一组接口，终端窗口只是视觉装饰](/screenshots/home-desktop.png)

![390px 窄屏：同一套组件收成单列，筛选与列表都不横向溢出，元数据自动折行](/screenshots/home-mobile.png)

截图不是装饰，是这一节所有机制的合并结果：路由懒加载、请求剥壳、筛选同步 URL、三态渲染，任何一环写错，页面都不会是这个样子。

**error 没做独立占位**，这是明确的债：请求失败时页面会停在"没有找到文章"，因为拦截器弹完提示、列表还是空数组。正确做法是加一个 error 状态和重试按钮。

### 分页参数的上限在后端

前端每页 10 条（`pageSize = 10`），后端默认 20、上限 100：

```go
const (
	DefaultPageSize = 20
	MaxPageSize     = 100
)
```

`binding:"omitempty,gte=1,lte=100"` 在 Gin 绑定那层就把 `page_size=999999` 拦掉了。前端传 10 只是产品选择，规矩由后端定——**前端传上来的数字不能被信任**，这条和后端不信任前端传的 `author_id` 是同一个原则。

## 这些债我认

写完这一层，重复是收掉了，但缺口也很清楚。

**没有请求取消。** 快速连续切筛选项时，如果第一个请求比第二个慢，后到的旧响应会覆盖新数据。正确做法是 `AbortController`，或者在拦截器里给每个请求打序号、只接受最新的那个。现在是靠"大多数情况下响应顺序一致"在赌。

**没有缓存层。** 每次进详情页都重新拉文章和评论，每次回首页都重新拉列表和分类。个人博客无所谓，但如果有人在地铁上反复点，流量是白花的。

**没有 TypeScript。** `request.get()` 返回 `any`，`data.list` 写成 `data.lists` 只有运行时才发现。这个项目的定位是学后端，前端就没上 TS，代价是接口字段改名时全靠手测。

**错误提示只有全局 ElMessage。** 两个请求同时失败会连着弹两层；长文案在小屏上会压住内容；也没有重试入口。

**路由级 loading 缺失。** 页面 chunk 加载那几百毫秒里界面是静止的，没有任何反馈。

**上传的差异只收了一半。** `uploadImage` 用 `FormData`，其他接口用 JSON——这类差异现在收在 `api/admin.js` 里（`uploadImage` 里造 `FormData`、`vite` 那边靠代理转发），但超时、重试策略没有按接口区分，统一 10 秒。

---

这一层真正的价值不在"封装得多优雅"，而在于：**页面里看不到 axios，看不到 `/api/v1`，也看不到错误文案**。改后端地址、加一个公共请求头、换掉提示组件，都只动一个文件。

下一篇换个角度，讲一件比请求更危险的事：正文用 `v-html` 插进页面。
