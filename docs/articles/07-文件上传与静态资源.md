后台写文章要能传封面和正文插图。第一反应是「收文件、改个名、存到 `uploads/`」，但把下面几个问题想一遍，就会发现它和用户输入一样，都是不可信输入。

1. 用户传的真是图片吗？如果他把一个 `.php` 改名成 `.png` 呢？
2. 文件名用用户给的？那 `../../etc/passwd` 会存到哪？
3. 图片存下来后，由谁发出去？Go 还是 Nginx？
4. 上限设多少？Nginx 和 Go 各管一层，漏一层会怎样？

这篇按这四个问题讲上传。代码在 `service/upload_service.go`、`handler/upload_handler.go`。

## 类型判断：只看内容，不看文件名

浏览器上传时会带一个 `Content-Type`，但它和文件名一样，是客户端说的，不能信。

服务端能信的只有文件内容本身。标准库提供了一个约定：读前 512 字节，用 `http.DetectContentType` 猜真实类型。

```go
head := make([]byte, 512)
n, _ := io.ReadFull(src, head)
mime := http.DetectContentType(head[:n])

ext, ok := allowedImageTypes[mime]
if !ok {
    return nil, fmt.Errorf("%w: 只允许 jpg/png/gif/webp 图片，识别到的类型是 %s",
        ErrInvalidInput, mime)
}
```

白名单只有四种：

```go
var allowedImageTypes = map[string]string{
    "image/jpeg": ".jpg",
    "image/png":  ".png",
    "image/gif":  ".gif",
    "image/webp": ".webp",
}
```

这里有一个很隐蔽的 bug，我第一次就踩了：**嗅探读走了 512 字节，文件指针已经不在开头**。如果直接 `io.Copy` 落盘，存下来的文件会少一截，图片打不开。

所以嗅探完必须回退：

```go
if _, err := src.Seek(0, io.SeekStart); err != nil { ... }
```

这不是可选的「优化」，是正确性。上传功能「返回成功但图片是坏的」，比直接报错更难查。

## 文件名：完全由服务端生成

绝不能用用户上传的文件名。原因不是「不好看」，是**路径穿越**：

```
文件名: ../../../../etc/cron.d/evil
```

如果代码写 `filepath.Join(uploadDir, fh.Filename)`，拼出来的路径可能跑到项目目录之外。不同系统对 `..` 和绝对路径的处理还不一样，靠过滤字符串很难做干净。

最彻底的做法是**根本不用它**：

```go
func randomFileName() string {
    var b [8]byte
    if _, err := rand.Read(b[:]); err != nil {
        return fmt.Sprintf("%x", time.Now().UnixNano())
    }
    return hex.EncodeToString(b[:])   // 16 位十六进制
}
```

用 `crypto/rand` 而不是 `math/rand`。后者的种子可预测，攻击者可能猜出已上传文件的 URL。图片本身不敏感，但如果上传的是「还没发布的文章封面」，猜 URL 就等于提前看到内容。

扩展名由嗅探结果决定（`.jpg` / `.png` …），也不取用户文件名。这样「文件名」这个输入从头到尾没有参与路径拼接。

## 目录结构：按年月分

如果所有文件都扔在 `uploads/` 下，一年后这个目录会有几万个文件。`ls`、备份、rsync、甚至某些文件系统的目录查找都会变慢。

所以按年月分：

```
uploads/
├── 2026/
│   └── 11/
│       ├── f3179b42636994bb.png
│       └── 8a02c7d1e5f64319.jpg
```

```go
subDir := time.Now().Format("2006/01")   // Go 的时间格式化用的是参考时间
dstDir := filepath.Join(s.dir, subDir)
os.MkdirAll(dstDir, 0o755)
```

URL 用正斜杠拼，不要用 `filepath.Join`：

```go
URL: "/uploads/" + subDir + "/" + name
```

`filepath.Join` 在 Windows 上会给反斜杠，浏览器不认。这种问题在 Mac 上开发永远遇不到，部署到 Linux 也没事，但只要有人在 Windows 上跑一次就会暴露。

## 大小限制：两层都要设

上传大小有两道闸：

1. **Nginx 的 `client_max_body_size`**：请求体超过就直接 413，根本进不到 Go
2. **Go 的业务上限**：`UPLOAD_MAX_MB`（默认 5MB），在 Service 里判断

```go
if fh.Size > int64(s.maxMB)<<20 {
    return nil, fmt.Errorf("%w: 图片不能超过 %d MB", ErrInvalidInput, s.maxMB)
}
```

两层的数字要匹配：Nginx 设 8m、后端设 5MB，用户传 6MB 的图会先到 Go 再被拒，体验是「等到传完才报错」；反过来 Nginx 设 2m、后端设 5MB，用户传 3MB 会直接被 Nginx 拒掉，前端拿不到后端的 JSON 错误。

所以部署时的规则是：**Nginx 的上限 ≥ 后端上限**，并且留一点余量给 multipart 的边界和表单字段。

## 图片存下来之后，由谁发出去

后端把 `uploads` 目录挂成静态资源：

```go
r.Static("/uploads", uploadSvc.Dir())
```

开发期这样够了。生产环境有两个选择：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Nginx 反代到 Go 的 `/uploads` | 配置简单，权限统一 | 每个图片请求都占一个 Go goroutine |
| Nginx 直接 `alias` 到上传目录 | 走 `sendfile`，不经过 Go，快 | 目录权限要单独配，路径要写对 |

项目默认用反代（`deploy/nginx.conf` 里的 `location /uploads/`），因为简单、不容易配错。流量大了再改成 `alias`，因为图片是纯静态文件，没必要让 Go 参与。

这也是第 01 篇那条分工的延伸：**动态接口归 Go，静态文件归 Nginx**。上传接口本身是动态的（要鉴权、要嗅探、要落盘），但上传完的图片是静态的。

## 这笔债

上传功能目前只做到「安全地存下来」，还有几件事没做：

- **没有图片压缩**：`UPLOAD_MAX_MB=5`，5MB 的图原样落盘，详情页原样加载。正确做法是上传前用 canvas 压一遍，或者服务端用 `imaging` 库生成缩略图。
- **没有对象存储**：图片在本机磁盘，备份要连目录一起备，扩容要迁数据。生产规模上来应该换 OSS/S3 + CDN。
- **没有防盗链/权限**：`/uploads/` 是公开的，知道 URL 就能访问。对博客图片没问题，对私有附件就不行。
- **没有清理机制**：换了封面，旧图还留在磁盘上。需要定期扫描「没有被任何文章引用的文件」再删。
- **上传接口只校验登录**，没有限制频率。理论上登录用户可以刷满磁盘。当前只有我一个人用，暂不处理。

这些不是「不会做」，而是当前规模下收益低于复杂度。写清楚边界，比假装完备更有用。
