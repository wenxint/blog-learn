"分层"这个词被讲烂了，但大部分教程只告诉你"要分层"，不告诉你**为什么分、每层不许干什么、以及分了之后要付什么代价**。

这篇讲我这套代码的五个格子，以及我在里面踩过的坑。

## 五个格子

![后端分层](/diagrams/layered.svg)

一句话概括每层的边界：

| 层 | 只做 | 绝对不做 |
|---|---|---|
| Handler | 绑参数、调 service、写响应 | 不写 SQL、不做业务判断 |
| Service | 业务校验、事务、状态流转 | 不碰 HTTP、不拼 JSON |
| Repository | SQL、分页、预加载 | 不做业务判断 |
| Model | 字段与表结构映射 | 不写查询、不带逻辑 |
| Middleware | 横切关注点（鉴权、日志、CORS） | 不碰具体业务 |

这些"不做"不是洁癖，是**每一条都对应一种真实会发生的腐化**。

比如 Handler 里写 SQL：一开始只是"顺手查个分类名"，三个月后 Handler 里有了三个查询和一个 if 判断，Service 变成一层空转发。等你想加缓存时，发现不知道该在哪加。

比如 Service 里碰 HTTP：它就拿不到 `*gin.Context` 之外的入口，于是**没法写单测**——测试一个业务规则要起一个 HTTP server。

## 依赖只能朝一个方向

图里那个"只能向下依赖"的箭头是硬约束。

Service import Handler → Service 和 Handler 互相 import → **Go 编译期直接报循环引用**，代码根本编不过。

这是 Go 语言给的好处：循环依赖是编译错误，不是靠人自觉。所以我从来没在这套代码里纠结过"依赖方向对不对"，编译器会告诉我。

## 装配：构造函数注入

所有依赖在 `router.New` 里一次性装配：

```go
db, _ := database.New(cfg)
articleRepo := repository.NewArticleRepo(db)
articleSvc := service.NewArticleService(db, articleRepo)
articleHandler := handler.NewArticleHandler(articleSvc)

api.GET("/articles", articleHandler.List)
```

没有全局单例，没有 `init()` 里偷偷建连接。每一层拿到的是结构体指针，构造完就不可变。

构造函数注入的**潜力**是「测试时塞假实现」：如果 Repository 抽成接口，Service 就能在不起数据库的情况下测业务规则。

```go
// 示意：当前代码还没有这层接口，Repository 传的是具体类型
type fakeRepo struct{ articles []model.Article }

func (f *fakeRepo) List(ctx context.Context, q ListQuery) ([]model.Article, error) {
    return f.articles, nil
}

func TestArticleListPagination(t *testing.T) {
    svc := service.NewArticleService(&fakeRepo{articles: seed})
    got, _ := svc.List(context.Background(), ListQuery{Page: 1, PageSize: 10})
    // 断言分页
}
```

**但这一步现在还没做到**：`NewArticleService` 收的是 `*repository.ArticleRepository`，不是接口，塞不进 `fakeRepo`。所以当前的 24 个单测全部集中在纯函数层（config / hash / jwt / ratelimit），业务规则仍然只有手测。

要补 Service 的测试，第一步是把 Repository 抽象成接口——这是一次小重构，会牵动 `router.New` 的装配代码。我在第 13 篇把它列进了下一步计划。

## 代价：一个接口改四个文件

诚实地说，分层是有成本的。

我想给文章加一个 `reading_time`（预计阅读分钟数）字段，得改：

1. `model/article.go` 加字段
2. 新建 `migrations/00X_add_reading_time.sql`
3. `repository/article_repo.go` 的 Select 列表加上它
4. `handler/article_handler.go` 的响应结构加上它

四个文件。如果是一坨代码，改一个文件就够了。

**那为什么还分层？** 因为在需求稳定的项目里，读代码的时间远超写代码的时间。而分层让"读"变便宜：找 SQL 就去 repository，找业务规则就去 service，找参数校验就去 handler，不用全文搜索。

这个博客我改了十几次需求（加置顶、加归档、加标签筛选、加评论审核），每次改动都只落在 1~2 层里。这种"改动范围可预测"的感觉，是分层真正卖的东西。

## 什么时候不该分层

三个信号，出现任意一个就该停手：

**一、CRUD 占 90% 的业务。** 如果一个接口就是"查表 → 返回"，中间两层纯转发，那 Service 是噪音。这种项目我会直接 Handler + Repository 两层。

**二、接口总数小于 10 个。** 分层是为了管理复杂度，复杂度不够时它只增加文件数。

**三、团队只有一个人且项目寿命短。** 你永远记得代码长什么样，分层反而让你每次改字段都要跳四个文件。

这个博客之所以分，是因为它同时满足：接口 34 个、要长期维护、我要拿它练"正规后端长什么样"。

## 一个反例：诊断接口没有分层

`/api/v1/debug/*` 那几个接口是故意不分层的：

```go
func (h *DebugHandler) DB(c *gin.Context) {
    sqlDB, _ := h.db.DB()
    stats := sqlDB.Stats()
    response.OK(c, gin.H{
        "open_connections": stats.OpenConnections,
        "wait_count":       stats.WaitCount,
    })
}
```

它们只在 `APP_ENV=dev` 时注册，纯粹是开发期工具，没有业务规则、没有复用价值。给它们套 Service 和 Repository 是教条。

**分层的判断标准不是"规范要求"，而是"这段逻辑有没有被复用或被单独测试的价值"。**

## 一条实操建议

如果你也在写类似的分层，别一开始就把五个格子画满。

我的顺序是：

1. 先 Handler 直接调数据库，跑通功能
2. 当第二个 Handler 需要同样的查询时，抽出 Repository
3. 当同一个业务规则在两个 Handler 里重复时，抽出 Service

**重构出来的分层，比预先设计的分层贴合实际。** 这套代码的 Service 层就是这么长出来的——最开始只有 Handler 和 Repository 两层。
