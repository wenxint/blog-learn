这个系列写到最后一篇，适合把账算清楚。

前面每篇都在讲「这里为什么这样」，但单篇只能看到一个点。把 13 篇放在一起，能看出一组共同的判断方式：**在当前规模下，什么复杂度值得引入，什么不值得。**

这篇讲三件事：做对的取舍、做错的取舍、以及下一步。

## 一组取舍

![五个关键决策：当前选择、付出的代价、以及什么条件下应该换掉它](/diagrams/tradeoffs.svg)

| 决策 | 当前选择 | 代价 | 什么时候该换 |
|---|---|---|---|
| 单体 vs 微服务 | 一台机器、一个 Go 进程 | 不能独立扩容，故障不隔离 | 有独立团队/模块流量差异大 |
| 进程内限流 vs Redis | 内存滑动窗口 | 多实例不共享，重启清零 | 部署第二个实例之前 |
| 本地磁盘 vs 对象存储 | `uploads/` 落盘 | 备份要连目录，扩容要迁数据 | 图片量上来或要多机部署 |
| JWT vs 服务端会话 | 无状态 JWT | 不能立刻踢人，改密后旧 token 仍有效 | 安全要求提高（后台、付费） |
| 客户端渲染 vs SSR | Vue SPA | SEO 差，首屏依赖 JS | 内容需要被搜索引擎收录 |

这五条不是「最优解」，是**当前约束下的解**。约束是：一个人维护、单机、低流量、以学习为目的。约束一变，答案就变。

最容易被忽略的是最后一列。很多架构讨论只争「哪个好」，不写「什么条件下换」。没有触发条件的取舍，过两年就变成「历史遗留」。

## 做对的三件事

**1. 先跑通，再抽象。**

Repository 和 Service 不是一开始画好的。第 6 课先把 SQL 写在 handler 里跑通，第 7 课发现第二个 handler 需要同样的查询，才抽出去。

这样抽出来的分层贴合实际。反过来，一开始就按「标准五层」铺满，很可能抽出三个纯转发的空壳。

**2. 错误统一翻译。**

Service 只返回 `ErrNotFound` / `ErrConflict` / `ErrInvalidInput` 这类语义错误，Handler 用一张 switch 翻译成 HTTP 状态码和业务 code。

好处是新增接口不用重新想「这个错误该回什么」，前端也不用维护一张巨大的「状态码 → 文案」映射。

**3. 迁移只加不改。**

`001` 到 `005`，没有任何一个文件被回头修改。加 `article_tags`、`comments` 都是新增文件。

这让「线上表结构是哪个版本」始终可回答。回滚代码时通常不需要回滚表结构，因为新代码总是兼容旧结构。

## 做错的三件事

**1. 最早把 SQL 写进 handler。**

第 7 课才重构出去。如果一开始就分，后面加标签筛选、归档、置顶时能少改很多地方。

但也要说清楚：**这个「错」是有价值的**。没有先写一版混在一起的代码，我不会真正理解分层解决了什么问题。教训不是「应该一开始就分」，而是「知道自己在欠什么，并且尽快还」。

**2. 鉴权中间件漏过 `Abort()`。**

校验失败写了 401，但没有 `return` / `Abort()`，业务 handler 继续执行。这个 bug 不报错、不崩溃，只会安静地放行。

它让我记住一条规则：**中间件里任何「拒绝」分支，都必须同时中止链路。**

**3. 限流状态放在进程内存。**

单机没问题，但它把「多实例部署」这条路提前堵死了。当时至少应该抽一个 `Limiter` 接口，后面换 Redis 不用改调用方。

现在代码里 `ratelimit.Limiter` 是一个具体结构体，Service 直接依赖它。换实现要改构造函数签名——不是大改，但本可以避免。

## 测试覆盖到哪里

当前 24 个测试，全部落在纯函数层：

| 包 | 数量 | 覆盖 |
|---|---|---|
| config | 7 | 环境变量、必填校验、DSN、脱敏 |
| hash | 6 | bcrypt 格式、校验、随机盐、72 字节上限 |
| jwt | 6 | 签发解析、篡改、错密钥、过期、alg=none、issuer |
| ratelimit | 5 | 窗口、超限、多 key、过期、重置 |

```bash
cd backend && go vet ./... && go test ./... -count=1
# 4 个包 ok，其余 no test files，1 秒左右跑完
```

![测试水位：纯函数单测已落地，service 层 mock 测试仍是缺口](/diagrams/test-layers.svg)

**没覆盖的是业务规则**：分页夹紧、评论两级校验、状态流转、事务回滚。这些目前只有 curl 手测。

要补这一层，得先把 Repository 抽象成接口，才能塞 fake。这是一次小重构，也是下一步最该做的事。

## 如果重来，顺序会变

```
pkg/（response / jwt / hash / pagination / ratelimit）
  → model + migrations
  → repository
  → service
  → handler + router
  → 前端
  → 部署
```

理由：底层包一旦定下来，上层就是填空。反过来先写 handler，底层会跟着业务细节长歪——比如 response 结构会被某个接口的特殊需求带跑。

但注意，这个顺序适合「已经知道要做什么」的第二遍。第一遍学习时，还是应该从能跑的最小闭环开始，否则会在抽象上花太多时间。

## 下一步

按优先级：

1. **给 service 层补 mock 测试**：分页、评论、事务是最容易改坏的部分
2. **加 CI**：`go vet` + `go test` + `pnpm build`，每次提交都跑
3. **限流换 Redis**：练习「有状态」带来的取舍，也为多实例做准备
4. **全文搜索**：先记录 `LIKE` 的真实耗时，再换 Meilisearch 对比
5. **监控与备份**：至少有一个「服务挂了会通知我」的机制

这些做完，这个项目才从「能上线的学习项目」变成「能长期维护的小系统」。

## 最后：我学到了什么

不是「学会了 Gin 和 Vue3」——框架 API 会忘，查文档就能捡回来。

真正留下的是三件事：

1. **一条完整的链路**：浏览器 → Nginx → Go → MySQL，每一层负责什么、出错时看哪里。这条链路想清楚之后，换语言、换框架，排查方法还是同一套。
2. **一种判断方式**：每个技术选择都问「它解决什么问题、付出什么代价、什么条件下换掉」。架构不是选最先进的，是选当前约束下最合适的。
3. **一个习惯**：把「应该没问题」变成「这条命令输出了这个」。测试、验收命令、诊断接口、上线清单，本质都是同一件事——**让结论有证据**。
