## 四、踩过的 8 个坑

### 坑 1：Go toolchain 下载失败（不是网速问题）

**现象**：`go version` 卡住 60 秒后报错

```
go: downloading go1.26.4 (darwin/arm64)
verifying module: ... dial tcp 108.177.97.110:443: i/o timeout
```

**根因**：不是下载慢，是 toolchain 下载后要连 `sum.golang.google.cn` 做 sumdb 校验，该地址被墙。只设 `GOPROXY` 无效；设 `GOSUMDB=off` 反而报 `checksum database disabled by GOSUMDB=off`。

**解决**：

```bash
export GOPROXY=https://goproxy.cn,direct
export GOSUMDB=sum.golang.org   # 关键：让代理代答 sumdb
go version                      # 首次会下载 toolchain，1~2 分钟
```

已写进 `deploy/build.sh` 作为默认值。

---

### 坑 2：Mac 上编出的二进制 Linux 跑不了

**现象**：`./bin/blog-server: cannot execute binary file`

**根因**：`make build` 没有指定 `GOOS`，在 macOS 上产出的是 `darwin/arm64`。

**解决**：交叉编译 + 关 CGO（避免服务器 glibc 版本不匹配）：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 make build
```

**验证**：`file bin/blog-server` → `ELF 64-bit LSB executable, x86-64, statically linked`。

---

### 坑 3：`.gitignore` 没保护 `.env.prod`

**现象**：生成 `backend/.env.prod` 后 `git check-ignore` 提示未被忽略。

**根因**：`.gitignore` 只有 `backend/.env` 一条，`.env.prod` 会直接进仓库 → **DB 密码和 JWT 密钥上 GitHub**。

**解决**：

```gitignore
backend/.env
backend/.env.*
!backend/.env.example
```

**验证**：`.env` / `.env.prod` / `.env.local` 均被忽略，`.env.example` 仍入库。

---

### 坑 4：后端只认 `.env` 这一个文件名

**现象**：生成了 `.env.prod`，但后端根本不读。

**根因**：`config.go` 里写死 `godotenv.Load(".env")`。

**解决**：加 `ENV_FILE` 支持（[backend/internal/config/config.go](../backend/internal/config/config.go)）：

```go
envFile, explicit := os.LookupEnv("ENV_FILE")
if !explicit {
    envFile = ".env"
}
if _, err := os.Stat(envFile); err == nil {
    godotenv.Load(envFile)
} else if explicit {
    return nil, fmt.Errorf("ENV_FILE 指定的配置文件不存在: %s", envFile)
}
```

**设计要点**：显式指定却找不到文件时必须报错，否则会「以为走了生产配置，其实用了默认值」。

**验证**（用不同 `DB_PORT` 区分）：

| 场景 | 输出 |
|---|---|
| 不设 `ENV_FILE` | `dial tcp 127.0.0.1:3306` |
| `ENV_FILE` 指向 prod | `dial tcp 127.0.0.1:3307` |
| `ENV_FILE` 指向不存在 | `加载配置失败: ENV_FILE 指定的配置文件不存在` |

### 坑 5：中文乱码（最隐蔽的一个）

**现象**：接口返回 `Go ä»Žé›¶å¼€å§‹`，不是终端显示问题（Python 解码后依旧乱码）。

**排查过程**：

1. 查库里字节：`SELECT HEX(SUBSTRING(title,4,1))` → `C3A4`（正确应是 `E4BB8E`）
2. 确认表 collation 是 `utf8mb4_0900_ai_ci`、服务端 `character_set_server=utf8mb4`
3. 查客户端：`character_set_client` / `connection` / `results` **全是 latin1**
4. 查 locale：`LANG` 和 `LC_ALL` **都是空的**

**根因**：macOS / 服务器上 `LANG` 为空时，mysql 客户端默认用 **latin1** 作为 `character_set_client`，把 UTF-8 的种子文件按 latin1 塞进库 → 双重编码（每个中文字符从 3 字节变 6 字节）。

**解决**：清空重导，且**所有导入命令都必须带 `--default-character-set=utf8mb4`**：

```bash
mysql -ublog --default-character-set=utf8mb4 blog < migrations/002_seed.sql
```

**验证**：`HEX` 恢复 `E4BB8E`，`bytes/chars` 从 `73/39` 变为正常的 `39/19`。

**已回写**：`README.md`、`docs/03-部署.md`、`docs/04-上线清单` 的迁移命令都加了这个参数。

### 坑 6：Vite 只绑 IPv6

**现象**：`127.0.0.1:5173` 打不开，`localhost:5173` 能开。

**根因**：Vite 默认 `host: 'localhost'`，macOS 上 Node 优先解析成 `::1`（IPv6），只监听 IPv6。

**解决**（[frontend/vite.config.js](../frontend/vite.config.js)）：

```js
server: {
  port: 5173,
  host: '127.0.0.1',   // 显式绑 IPv4
  ...
}
```

### 坑 7：域名 `clientHold`

**现象**：阿里云控制台显示「实名认证成功」，但全球解析 `NXDOMAIN`。

**关键证据**：RDAP 里 `last changed` 停在 `2026-07-01T08:21:29Z`，五个月没动 —— 说明**注册局侧从未收到解除请求**，控制台的「成功」只代表阿里云审核了身份证。

**根因**：域名被注册商置为 `clientHold`（实名未通过/信息未同步），注册局因此不发布 NS 委派，递归解析器在 `.xyz` 层就返回 NXDOMAIN。

**解决**：完成实名认证后等待注册局解除。实测解除时间 **17:10（`last changed` 更新为当天）**，之后解析约 **29 分钟后**（17:39）全球生效。

**教训**：判断域名能不能用，**以 RDAP 和实际解析为准，不要看控制台面板**。

```bash
# 权威判断
curl -s "https://rdap.centralnic.com/xyz/domain/youzhichong.xyz"
curl -s "https://dns.alidns.com/resolve?name=youzhichong.xyz&type=A"
```

### 坑 8：阿里云 CLI 的凭据配置

**现象**：`aliyun ecs DescribeSecurityGroups --RegionId cn-shenzhen` 报 `region can't be empty`。

**排查**：环境变量 `ALIBABA_CLOUD_ACCESS_KEY_ID` 和命令行参数 `--access-key-id` 都不生效；`aliyun configure set --config-path` 也不写文件。

**解决**：直接写默认配置（服务器上原本无配置），用完立刻删除：

```bash
aliyun configure set --profile default --mode AK \
  --access-key-id '...' --access-key-secret '...' \
  --region cn-shenzhen --language zh

# 用完后必须清理
rm -f ~/.aliyun/config.json
```

**安全教训**：AccessKey 在对话/聊天中明文传递 = 已泄露。操作完成后应立即去控制台禁用。更安全的长期方案是**实例 RAM 角色**（密钥不落盘）。

## 八、关于「部署方式」的说明

这次不是你在控制台点击部署的，也不是我凭空操作的。实际过程是：

1. **你**在本地执行 `ssh-copy-id`，把公钥装到服务器（`~/.ssh/id_ed25519.pub`）
2. **我**通过 `ssh root@47.119.155.176` 免密登录，在服务器上逐条执行命令
3. 每一步执行完都立刻验证（`curl`、`systemctl status`、`ss -lntp`、`HEX()` 查字节）

所以严格说：**基础设施是你提供的（SSH 访问权 + 阿里云资源），执行是我远程做的**。

如果你想完全自己复现这个过程，见 [06-自助部署手册.md](06-自助部署手册.md) —— 那份文档假设没有任何 AI 辅助，所有命令都写全了。
